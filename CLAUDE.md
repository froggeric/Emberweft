# CLAUDE.md — guidance for AI assistants working on Emberweft

Emberweft is a native macOS (Apple Silicon, Metal 4) re-implementation of Scott Draves' **fractal flame** algorithm — the basis of the *Electric Sheep* screensaver. It is a generative-video studio: realtime playback of morphing flame "sheep", long-form export, audio-reactive music videos, a macOS screensaver, and multi-resolution output up to 4K.

## Core engineering rules (do not violate)

1. **Reference-then-Optimize.** `FlameReference` (CPU, Swift) is built and proven first, then `FlameRenderer` (Metal) is validated against it. Do not build Metal behavior that isn't matched by the CPU oracle.
2. **Determinism is mandatory.** Same genome + seed + params → identical frame within a backend, run after run and machine to machine. CPU and Metal are independent deterministic backends that agree within the parity threshold (PSNR ≥ 38 dB, SSIM ≥ 0.95); they are not required to be byte-identical to each other.
3. **Test-first.** Write the failing test (golden / parity / unit) before the implementation that satisfies it.
4. **No surprise external dependencies.** Prefer Apple SDKs only (Foundation, Metal, AVFoundation, Accelerate). Any new dependency needs explicit approval.
5. **Swift 6 strict concurrency.** Mutable state is actor-isolated or `Sendable`; Metal command recording is `@MainActor` where the API requires it.
6. **Faithful flam3 port.** The CPU reference renderer is a faithful Swift port of flam3's algorithms (affine convention, variation formulas, ISAAC RNG + consumption order, density estimation, display pipeline) — port the logic for correctness and parity, do not approximate or reinterpret. The affine/atan bugs found via the parity oracle are the exact class of error faithful porting eliminates.
7. **License posture — owner's decision (under review).** Emberweft is currently **source-available** (PolyForm Noncommercial). Because the renderer ports flam3, the final license (including any GPL implications) is the owner's call and under review — do not assert a license constraint either way, and do not impose GPL-avoidance, until the owner decides.

## Conventions

- **Commits:** Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `perf:`, `chore:`), small and focused, branch-per-feature, PRs into `main`.
- **Formatting:** `swift-format` (config in `.swift-format`).
- **Code identifiers** use the neutral `Flame` prefix (`FlameKit`, `FlameRenderer`, …); the **brand name Emberweft** is used only for user-facing artifacts (app bundle `EmberweftApp`, screensaver `EmberweftScreenSaver`, the `emberweft` CLI).
- **Deployment target:** macOS 26 (Metal 4), Apple Silicon (M1+). Intel unsupported.
- **`genomes/`** is an intentional ~1.6 GB data-preservation archive of ~123k Electric Sheep `.flam3` genomes (gens 165–248), split into `sheep/` (stills) + `edges/` (stored transitions) + an `edges.sqlite` pair DB — do not gitignore or remove. Gen 248 is a live flock (a local launchd job `com.emberweft.sheep-sync` syncs it daily). See `genomes/README.md`.
- **M3 animation** is a faithful flam3 port. `sheep_loop` (loop) = **pure affine rotation** `R(θ)·M` (θ=blend·360°) of each xform's pre-affine 2×2 only — the **palette is static** during a loop (seamless because `R(360°)=R(0°)`; palette motion is transitions-only). `sheep_edge` (transition) = align+special-sauce-pad → rotate both → interpolate A→B with `interpolation_type=log` + HSV palette blend. See [docs/rendering/transitions.md](docs/rendering/transitions.md) and the M3 spec; treat the archived genomes (flame counts, `time` values, `edges.sqlite`) as ground truth — don't re-derive the mechanics.
- **Seamless transitions need motion blur:** `--temporal-samples 1` means *use the genome default* (≈1000, Metal-capped 64) — NOT 1 sub-pass; pass `2` for near-sharp. Low temporal → a "brutal" mid-transition morph. Proven recipe: `emberweft animate …05739… …31943… --temporal-samples 32 --frames 160 --loop-cycles 1 --backend metal` (the `/tmp/m3_mb` reference).
- **flam3 parity oracle (M3+):** not installed / no Homebrew formula — build `scottdraves/flam3` from source (autotools + zlib/libpng/libxml2), drive via **env vars** (`flam3-genome` `sequence=`/`rotate=`/`inter=` → `flam3-animate`); disable its motion blur with genome attrs `passes=1 temporal_samples=1`. On this machine the built oracle is symlinked at `~/.local/bin/flam3-*` → `~/flam3-oracle-src/flam3/` (source survives there; `/tmp` builds get evicted on reboot — re-point the symlinks if `flam3-render` goes missing). Full detail in the [M3 spec](docs/superpowers/specs/2026-07-17-m3-animation-design.md).
- **Driving the flam3 oracle (concrete gotchas):** `format=png` is lowercase (PNG is rejected); a multi-keyframe sequence needs a `<flames>` wrapper around the `<flame>` elements (two bare flames won't parse); env `quality=` does NOT override the genome's `quality` attr (sed the genome to a low value like `quality="40"` or it renders at 2000 and hangs); `flam3-animate`'s `nframes` is unreliable — for one interpolated frame prefer `flam3-genome` `inter=`/`rotate=` → `flam3-render`.
- **Metal↔CPU on spiky stills is Float-limited** (~33 dB on e.g. `244.00788`, under the 38 gate) — fundamental: MSL has no FP64, and double-single emulation doesn't close it (the gap is the `(x,y)` Float trajectory diverging, not color precision). CPU is the oracle (faithful to flam3); accepted, not a bug. See `docs/superpowers/plans/2026-07-23-metal-step-port.md` — **don't re-attempt a Metal STEP/double port**.

### Metal & Swift 6 gotchas
- **`.metal` files:** SwiftPM does not compile them. Bundle as `resources: [.copy("Metal")]` + `exclude: ["Metal"]`, load at runtime via `Bundle.module` + `MTLDevice.makeLibrary(source:)`.
- **Distributing the release binary:** `make dist` ships **`dist/Emberweft.app`** (double-clickable GUI — launching the bare `emberweft-gui` executable instead makes Finder open it *through Terminal*, the lingering-Terminal-window symptom) plus the bare **`emberweft` CLI** beside its sibling `emberweft_FlameRenderer.bundle` (the Metal shaders load from it via `Bundle.module`; the bare executable fails `--backend metal` without it, CPU still works). The `.app`'s resource bundles (`emberweft_FlameRenderer.bundle` + `emberweft_EmberweftGUI.bundle`) live at the standard `Contents/Resources/` — but **SwiftPM 6's generated `Bundle.module` accessor does NOT search there**: its only candidates are `Bundle.main.bundleURL/<name>.bundle` (the `.app` root — where `codesign` rejects foreign entries: "unsealed contents present in the bundle root"; root symlinks are rejected too) and a compile-time `.build` path that only exists on the build machine (a bundled app with plain `Bundle.module` crash-exits with "could not load resource bundle" — verified empirically by moving the bundles around all three layouts). Hence `FlameRenderer/ModuleResources.swift` + `EmberweftGUI/AppModel.moduleBundle` resolve `Bundle.main.resourceURL` FIRST, falling back to `Bundle.module` (bare CLI / `swift run` / tests find the same sibling bundle either way — don't "simplify" them away, and re-verify the bundled app stays alive if you touch them). `make dist` also ad-hoc codesigns the `.app` and clears its quarantine xattrs; the Info.plist version comes from `git describe --tags --abbrev=0` (Makefile `APP_VERSION`, `v` stripped, `0.0.0` fallback). `swift build -c release` is arm64, links only system frameworks (no bundled dylibs; runs on any macOS 26 Apple Silicon machine); for zipped transfers users still clear quarantine with `xattr -dr com.apple.quarantine Emberweft.app` (CLI: `xattr -dr com.apple.quarantine emberweft emberweft_FlameRenderer.bundle`).
- **`gh release` (create/upload/edit) runs from the repo dir** (or pass `-R froggeric/Emberweft`): it shells out to `git`, so invoking it from `/tmp` fails "not a git repository" even when the asset path is elsewhere. **Release asset:** `cd dist && ditto -c -k --keepParent Emberweft.app emberweft-v<X.Y.Z>-macos-arm64.zip` (matches the v0.6.0/v0.6.1 naming); run `make dist` FIRST so Info.plist picks up the new tag; notes include the quarantine-clear line for the un-notarized zip.
- **CHANGELOG discipline:** log every owner-facing fix/feature under `CHANGELOG.md` `[Unreleased]` **when it lands** (create the section if absent — v0.6.1 shipped with two unlogged fixes that had to be reconstructed from `git log`). Pre-release sweep: `git log $(git describe --tags --abbrev=0)..HEAD --oneline` vs the `[Unreleased]` section.
- **Release + docs pass recipe:** version = the tag (`git tag vX.Y.Z`; house style: 0.x features ship as PATCH bumps — v0.6.1 carried "Added" entries). After tagging, run the docs sweep: roadmap (milestone header ✅ + Current Status line + milestone table), README (status line, milestone table row, flag docs, "what works" paragraph), architecture component sections (M6.5 shipped with NO FlameFlock section — new modules need one). If docs land after the tag, move it: `git tag -f vX.Y.Z && git push -f origin vX.Y.Z`.
- **GitHub release notes:** write plainly and factually, no em dashes (use commas, periods, colons) and no AI marketing tells ("leverage", "delve", "robust", overusing "seamless", etc.). The owner's stated preference for release descriptions. Pass notes inline (`gh release create … --notes "$(cat <<'EOF' … EOF)"`) rather than a temp file, which would need separate cleanup.
- **The Bash tool's working directory persists across calls.** A `cd` for a smoke launch (e.g. `cd dist && ./emberweft-gui &` or `cd .build/.../debug`) leaves every later command running from that dir, so a following `git add Sources/…` fails "pathspec did not match." Use absolute paths or `cd` back to the repo root first.
- **Pass large structs by `thread const&`, not by value, in Metal kernels.** Passing a big read-only struct (e.g. `GPUXform`, 906 floats / 3624 B) *by value* to `static inline` helpers destabilizes the Metal compiler's FP instruction scheduling — on fragile attractors the re-scheduled Float trajectory diverges → empty `RGBA(0,0,0,0)` frames + nondeterminism (rule #2 break). This was the v0.1.2→v0.1.3 empty-frame regression (commit `938a855a2`): it passed `SpecialSauceParityTests` (single-variation) but broke real multi-xform animations. Signature fix: `f(GPUXform x, …)` → `f(thread const GPUXform& x, …)`. Not caught by fast-math toggling or struct-layout checks — it's pure codegen.
- **Metal `float` cosh/sinh/exp overflow → clamp the arg to ±88.** Metal `cosh(arg)`/`exp(arg)` overflow to `+Inf` at arg≈89/88.7 where CPU `double` is finite → `0.0f * Inf == NaN` → chaos-game trajectory collapse (v0.1.4, commit `a45ce3d6b`). 15 hyperbolic/trig/exp variations (`coth cot sinh cosh tanh sech csch csc sec exponential cosine exp sin cos tan`) clamp the overflow-prone arg to `[-88,88]` before the call — bit-identical for normal args (parity tests pass), captures CPU's saturated limit for large args. If porting a new variation using cosh/sinh/exp, apply the same clamp.
- **Variation param interpolation is per-param linear (flam3 `INTERP`), NOT "A wins".** `GenomeInterpolator.mergeLog` must interpolate each parametric field `(1−t)·a + t·b` (descriptor defaults when a side lacks the param). The old "A's params win, B fills gaps" bled A's params into the result at t=1 (v0.1.5, commit `052dcceaf`) — broke transition endpoints (`Transition(A,B,1.0)≠B`). flam3 has no `merge_log`; its variations are a fixed `var[N]` array `INTERP`'d slot-by-slot (interpolation.c:543-700).
- **GenomeInterpolator must port ALL flam3 INTERP fields, not just matrix/xform/palette.** The `blend` skeleton must interpolate (or copy-from-`cpi[0]`) every field in flam3's `INTERP` block (interpolation.c:464-700) — including the Quality display scalars (brightness, gamma, vibrancy, highlight_power, filter radii, estimator params). Any `t < 0.5 ? a : b` hard-cut or silently-dropped field is a latent transition-smoothness bug (v0.1.5: mergeLog/paletteMode; v0.1.6: Quality hard-cut).
- **The `.log` matrix det guard is intentional, not unfaithful.** Opposite-handedness xform pairs (det A·det B < 0) cross det=0 at the polar-log midpoint → singular matrix → density spike. The guard in `interpolateAffineLog` (v0.1.6) falls back to `lerpAffine` for these pairs. flam3 has the same singularity (faithful artifact); the guard is an intentional seamless divergence per the owner — don't remove it.
- **`Camera.scale` log-space interpolation is intentional, not unfaithful.** flam3 INTERPs `pixels_per_unit` *linearly* (interpolation.c:489), but Emberweft interpolates `Camera.scale` in *log-space* (geometric mean `pow(a,1−t)·pow(b,t)`) in `GenomeInterpolator.blend`. Magnification is perceived logarithmically (Weber-Fechner), so log-space gives constant *perceived* zoom velocity and a perceptually-symmetric midpoint — the seamless choice for ambient playback; it can diverge ~21% from flam3 at the midpoint of high-ratio edges (e.g. 400→110). `zoom` and `rotation` stay *linear*, and that is also intentional: `zoom` is already log-coded in the projection (`pixelsPerUnit = scale·2^zoom`, so linear-in-zoom = geometric-in-magnification) and angle is perceived linearly. Rule of thumb: log-space only for linear-coded + log-perceived magnitudes (`scale`); linear for log-coded params (`zoom`) and linearly-perceived quantities (`rotation`, `center`, `time`). Pinned by `testScaleLogSpace` — don't revert to linear in a flam3-parity pass.
- **Loop→transition boundary: realtime short-circuits to pure-A; OFFLINE does NOT (temporal blur handles it).** flam3's `sheep_edge` fires its `seqflag && blend==0` shortcut PER SUB-FRAME (flam3.c:476-477), returning A un-aligned only at the exact `blend=0` sub-frame — so its motion blur survives and averages out the faithful `.log` polar round-trip residual (~15 MAD at ts=1 → ~6 at ts=32). Emberweft mirrors this split: `PlaybackDispatcher` (realtime, no blur) renders the fromSheep directly at the boundary via `Schedule.isLoopToTransitionBoundary` (faithful to flam3's seqflag for single-frame). `AnimateCommand` (offline, ts>1) does **not** short-circuit — a per-frame short-circuit returns the SAME genome for every sub-frame, making the boundary frame SHARP while its neighbors are motion-blurred → a sharp-vs-blurred "complexity jump" (~30 MAD at ts=32; the v0.1.8 regression, reverted v0.1.9). The offline boundary relies on temporal blur to average the residual's per-pixel DECORRELATION (~6 MAD at ts=32) — but NOT the larger variation-LEAK over-bright (blur-invariant; see the leak-clip gotcha below). Don't re-add the offline short-circuit; don't centralize into `Transition.blend` (its `t==0` is never reached by the 1-indexed schedule).
- **One-sided variation-leak clip is intentional, not unfaithful (the blur-invariant boundary over-bright).** Temporal blur cancels the `.log` polar-residual DECORRELATION but NOT the larger variation-LEAK over-bright: flam3's `INTERP(xform[i].var[j])` (interpolation.c:654) emits tiny nonzero weights (~t·B.weight) for every variation B has that A lacks (one-sided), and on spiky attractors these chaotic leaks redecorate the canvas — e.g. 05915→37205 slot-2 (horseshoe/fan2/mobius/cot/lazysusan) fills ~30% more histogram bins at the boundary, +38% luma, **blur-invariant** (the loop, which doesn't interpolate, is clean → the user-visible "elements appearing" jump). `GenomeInterpolator.mergeVariations` clips one-sided leaks: drops variations whose raw weight is 0 on **exactly one** side (detected by per-side RAW weight, not name — `align`'s parametric-param copy adds B's parametric variations to A at weight 0, defeating name-presence) AND whose merged weight < ε=1e-3. Both-zero slots are kept (flam3's full `var[]` array); two-sided kept; leaks fade in once weight ≥ ε. flam3 does NOT clip (faithful, confirmed via the oracle; q-dependent — worse at low q where the background isn't filled) — a deliberate seamless divergence, like the `.log` det guard. Pinned by `testMergeClipsOneSidedLeaksBelowEps`. (Root-caused by instrumenting — 4 wrong theory-only guesses failed; always dump+measure a render-brightness bug.)
- **Diagnosing render/transition brightness defects:** compute per-frame mean luma + sharpness (Laplacian variance) + consecutive-frame MAD on the PNG sequence with python+PIL (no swift) — it pinpoints which frame/segment/boundary a density or brightness shift occurs at, and whether it's a sharpness (blur) or luma (density) problem. The v0.1.10 variation-leak over-bright was isolated this way after four wrong theory-only guesses.
- **Empty/transparent Metal frames** are `RGBA(0,0,0,0)` — white in a PNG viewer, black in an alpha-flattened (`-pix_fmt yuv420p`) video. Detect via `max(pixel)==0`; isolate Metal-vs-logic by re-rendering the same frame on **CPU** (the oracle — if CPU is fine, it's Metal-specific).
- **NaN-camera archive genomes:** ~1.4% of gen-248 sheep have `center="nan nan" scale="nan"` literally in their `.flam3` headers → always render solid black on BOTH backends (data-integrity issue, not a code bug). `validate` doesn't catch it. Exclude NaN-header genomes from renders or add a defensive parser check. gen-248 also carries degenerate `scale` values (negative like `-259`, tiny `6e-05`, huge `5760`) — same data-integrity class; sanity-check `scale > 0` and in-band when picking render subjects.
- **Sampling genomes by generation:** use `sheep/gen-248/` directly, NOT `find … -path '*248*'` — that matches sheep *IDs* like `169.03248` (gen-169), a different population (index palettes + `hue`) from gen-248 (explicit `<color>` palettes, no `hue`). Once poisoned a faithfulness audit.
- **Pipeline-state API:** use `library.makeFunction(name:)` (optional) + `device.makeComputePipelineState(function:)`. The `makeFunction("x")!.makeComputePipelineState()` form does not compile on the macOS 26 SDK.
- **Off-main Metal render path (M4 thumbnails):** `MetalRenderer.render` is `@MainActor` + sync (`waitUntilCompleted` on main) → ~36 ms of per-render host overhead that freezes the UI (resolution-independent — the cost is buffer alloc + commit + wait, not GPU compute). The thumbnail path uses `MetalRenderer.renderOffMain` instead: it runs `renderFusedCore` (the actor-agnostic extraction of `renderFused`, taking device/queue/PSOs as params) on a dedicated background `DispatchQueue` with its own `MetalOffMainCache` (device/library/queue/PSOs serialized via the queue). Never touches the MainActor → no freeze. The realtime `@MainActor` path is unchanged. Output is **byte-identical** to the main path (pinned by `testRenderOffMainMatchesMainActorPath` / `…OnRealGenome`). The pure host helpers (`MetalHost`, `DisplayPipelineMetal.makeSpatialKernelMetal`/`DisplayParams`) were de-isolated (their `@MainActor` was conservative — they're pure compute) so `renderFusedCore` can call them off-main; `DisplayPipelineMetal.render` stays `@MainActor`. CPU thumbnails are also off-main (`ReferenceRenderer` is not MainActor) but ~too slow at high res — Metal-off-main is the default.
- **Two CGImage orientations — don't mix them (the thumbnail-vs-playback flip, M4).** `FlameUI.makeCGImage` (FlamePlayer) **flips rows** — it's built for `CAMetalLayer.contents`, which displays the renderer's top-first data bottom-up, so the flip restores upright (M3-verified). `RGBA8Image.toCGImage()` (EmberweftUI) is **upright / no-flip** — the renderer's `pixels` are already top-first (a CGImage's native layout), matching `writePNG`/`readPNG` whose orientation is verified vs the `flam3` goldens. Use `toCGImage()` for `NSImage`/SwiftUI `Image` and any pixel processing (downscale, etc.) — NOT `makeCGImage`. The M4 bug: `scaled()` called `toCGImage()`→`makeCGImage` (a layer-flip) in an intermediate downscale step, then `toNSImage()` flipped again → double flip vs playback's single flip. Pinned by `testScaledPreservesTopBottomOrientation`.
- **SwiftUI sheet + `@State` view-model teardown leak (M4).** A `PlaybackDispatcher` runs an infinite `run(frameCount: .max)` loop. If its owner is `@State` on a sheet and dismissal fires `beginStop()` with `[weak self]`, SwiftUI releases the view-model before `stop()` runs — but the in-flight `await dispatcher.run(...)` keeps the actor alive via the async call → GPU busy forever. Fix: `beginStop()` captures `self` **strongly** (keeps the VM alive just long enough to stop, then clears `stopTask` to break the self→stopTask→task→self cycle), AND the Close button does `Task { await vm.stop(); dismiss() }` (stop-before-dismiss). `.onDisappear` alone is unreliable for sheets.
- **Bare-executable SwiftUI app must set its activation policy (M4).** A `@main App` run as a SwiftPM executable (no `.app` bundle) defaults to an activation policy where it **cannot become the key app** — keyboard goes to the launching shell (e.g. the Claude Code session) and the window isn't fully interactive (no key events, click-through fails). `NSApp.activate(ignoringOtherApps:)` alone isn't enough. Fix: an `AppDelegate` (`@NSApplicationDelegateAdaptor`) calls `NSApp.setActivationPolicy(.regular)` then `NSApp.activate(ignoringOtherApps: true)` in `applicationDidFinishLaunching` (`Sources/EmberweftGUI/EmberweftApp.swift`). When launching the binary for someone from a shell, also `cd` into the dir holding the resource bundles so `Bundle.module` resolves.
- **Bundle-less SwiftPM-executable SwiftUI app: system drag-and-drop is unreliable for in-app reordering (M4).** On a SwiftPM executable with no `.app` bundle, `.draggable` + `.dropDestination` (with a custom `Transferable`) and `List` + `.onMove` do not work for in-grid reorder: the drop action never fires (or the drag never starts), and `List.onMove` replaces the grid with a `List` (a regression when you want to keep the `LazyVGrid` card look). The working pattern is a **custom in-app `DragGesture`**: a per-cell `DragGesture(minimumDistance: 10)` (so taps and in-cell Buttons still work) lifts the cell, each cell publishes its frame + STORED index via a `PreferenceKey`, the drag's `onChanged` hit-tests the pointer (source center + translation) against the collected frames (sorted by stored index, rule #2: a by-key map read, never a float sum over a hash collection) to find the drop target, and `onEnded` calls an `Array.move`-backed `CollectionsStore.moveEntries(in:from:to:)`. No pasteboard, no `UTType`, no `List`. Reference: `LibraryView`'s collection reorder (`collectionCell` / `collectionDragTarget` / `CollectionCellFramePreference`). The two failed approaches are documented in the `LibraryView.collectionGridBody` comment so they aren't retried.
- **GUI has no test target:** `EmberweftGUI` (the app) has NO test target. All testable GUI logic lives in `EmberweftUI` (tested via `EmberweftUITests`, 129 tests). `EmberweftGUI` views are verified manually. This drove the module split (testable types = `EmberweftUI`; thin SwiftUI wiring = `EmberweftGUI`).
- **SwiftUI `@Observable` stores are `@MainActor` classes, not actors:** MetadataStore, CollectionsStore, FacetCache, AppPreferences are all `@MainActor @Observable final class` (sync SwiftUI reads in View bodies). Off-main persistence via coalesced `Task.detached` inside the class. To get `$model.prefs` bindings from `@Environment(AppModel.self)`, add `@Bindable var model = model` inside the View body.
- **Modifier-click detection in SwiftUI grids:** `.onTapGesture { let mods = NSEvent.modifierFlags; ... }` is the pragmatic pattern for cmd/ctrl/shift-click in `LazyVGrid` cells. The `.modifierKeys()` gesture API was unreliable in complex view hierarchies with nested Buttons.
- **Context menus are AppKit-native, NOT SwiftUI `.contextMenu` (v0.6.1):** SwiftUI tore grid-cell menu sessions down on view re-renders (thumbnail load, `@Observable` publishes) — menus vanished before the user could click, worst on the Add-to-Collection submenu. Use the existing `Sources/EmberweftGUI/AppKitContextMenu.swift` bridge (`.overlay(AppKitContextMenu { NSMenu … })`). Four load-bearing gotchas it already handles: (a) the host must be an OVERLAY — AppKit's hit-test is top-down and a `.background` host loses to hit-testable SwiftUI content (`MenuHostView.hitTest` claims the hit only for right/ctrl-clicks); (b) **`NSMenuItem.target` is WEAK** — a closure box set as target deallocates once the menu is built and clicks dispatch into the void; the box is retained via `objc_setAssociatedObject` (key is `nonisolated(unsafe) static var`); (c) `autoenablesItems` validation greys closure-backed items — the built tree opts out; (d) actions defer one run-loop turn (`NSObject.perform(#selector, afterDelay: 0)`) so SwiftUI sheets present after menu teardown (`DispatchQueue.main.async` hits Swift 6 `@Sendable` walls).
- **Debugging GUI interaction bugs — instrument, don't theory-iterate:** build debug, launch `.build/arm64-apple-macosx/debug/emberweft-gui > /tmp/log 2>&1 &` from an absolute path, add temporary `NSLog("DIAG …")` at each link in the suspect chain, and have the owner perform the action once — NSLog also appears in the unified log (`log show --predicate 'eventMessage CONTAINS "DIAG"'`). The v0.6.1 menu fix was found this way after three wrong timing theories (the log proved the action never fired = weak-target dealloc, not run-loop timing). Verify the chain end-to-end, then strip the diagnostics before committing.
- **Preview presets + live FPS (v0.3.1):** both playback windows carry a `PreviewPerfCluster` (FPS readout + `slider.horizontal.3` trigger) in the transport bar. `AppPreferences.PreviewPreset` (draft/balanced/quality/custom) is the single source of truth for `previewParams()` (named presets derive w/h/spp/oversample from the enum; `.custom` reads the raw `previewWidth/Height/SamplesPerPixel/Oversample` fields). Additive `FlameExport` only (`renderSegmentRange`, `concat`, `VideoEncoder` metadata — all DEFAULT-byte-identical; the animate↔export byte-identity pin holds). `FlameKit`/`FlameReference`/`FlameRenderer` UNTOUCHED (parity gate = `git diff --name-only main` empty for those dirs). **CLI:** `emberweft flock generate|stitch|browse|rebuild|export-list` (`flock` is `nonisolated async`; Metal probed via `await MainActor.run { MetalRenderer.isAvailable }` from the async context, never from a non-main actor/sync method — it traps; SIGINT via `DispatchSource.makeSignalSource`, the existing pattern). Spec: `docs/superpowers/specs/2026-08-12-m6.5-flock-archive-design.md`; plan: `docs/superpowers/plans/2026-08-12-m6.5-flock-archive.md`.
- **Stitch seam jump — ROOT CAUSE = smoothing windows clipping at artifact boundaries (M6.5 seam fix, geometry v2):** the stitched archive timeline showed 1-frame jumps at every file seam (edge→loop up to **35.6×** the local MAD baseline with Δluma −76, loop→edge 17.7×/+61, loop→loop repeat 7.3×), while the inline one-shot export of the same genomes/settings was smooth (its own seams ≤3×). Measured isolation: with smoothing OFF the SAME stitch was already clean (0.96–1.2×) and the sharp boundary frames match across the seam (MAD 0.52 at t=1) — the CONTENT/endpoint hardening and PTS were fine; the defect was purely that each standalone artifact's centered box window (h=5) is one-sided at its frame range, and because DE+display on the AVERAGED histogram tracks the BRIGHTEST window member (γ≈4.65 compresses density ratios — halving a bin's density only drops brightness ~10%), an edge whose mid-morph is 2–4× brighter than both endpoints makes the boundary frames on the two sides of a seam wildly different. **Fix = seam-aware artifact geometry (`ArchiveRenderer.SeamGeometry`, catalog `geom` v2), no FlameKit/FlameExport/renderer change:** a loop unit is TWO files — CORE (phases `[h, L−h)` of a 1-cycle plan, all windows interior) + WRAP (frames `[2L−h, 2L+h)` of a **3-cycle** plan, `loopCycles: 3` ⇒ same per-frame angular velocity, the wrap frames straddle the cycle wrap with interior windows — a loop is periodic so this needs no cross-unit context); an edge is the **3-segment** plan `loop(A)+edge+loop(B)` encoding `[L−h, L+T+h)` (the transition plus h boundary frames of each neighbor; its transition-slot descriptors are IDENTICAL to the old 2-segment plan's). The stitch assembles `[core, (wrap, core)×(r−1)] , ext, …` (a trailing wrap closes the final cycle) — every consecutive frame pair across every seam shares 2h of its 2h+1 window members, exactly like the inline timeline. Post-fix ALL seams 1.0–2.7× baseline (inline-parity), max Δluma +7.6. `geom` is an EXACT hit-gate (like `codec` — v1 rows MISS and re-render; NOT a rank), schema v1→v2 migrates in place (ALTER + default 1). Timeline starts at phase h and ends at L−h (h frames unplayed at each end — imperceptible, documented divergence). The pinned tests: `testSeamHalfWidthMatchesSmoothingCap` (geometry h must move with `TemporalSmoothing.centeredHalfWidth`), the interior-window/legacy-descriptor/3-cycle-phase pins, the v1-migration + geometry-gate tests.
- **`AsyncThrowingStream` + consumer `Task.cancel()` race (the stuck-Cancelling bug, v0.6.0):** cancelling the CONSUMING task ends its `for try await` early and DISCARDS the producer's subsequent terminal event (the catch only runs on a throw; an early normal end runs nothing) — a cancel-requested run whose producer yields `.cancelled` a few frames later never lands a terminal state and the UI sticks. Fix pattern: after the loop ends normally, land the terminal yourself (`if cancelRequested && !isTerminal { state = .cancelled }` — `FlockModel.landCancelled…IfNeeded`, both generate + stitch twins). Diagnose stuck-state/hang bugs with an INTEGRATION repro (real actors + a tiny real render + poll-with-timeout; never `await` the possibly-hung task) plus print-instrumenting each leg — layer-by-layer spy tests miss cross-layer races (repro: 10 s stuck pre-fix, 0.19 s green post-fix).
- **ArchiveRenderer MUST thread `settings.temporalSamples` into its FramePlans — the genome's ts is NOT the tier's:** the original `makeLoopPlan`/`makeEdgePlan` passed `A.quality.temporalSamples` (≈1000 on real ES genomes, Metal-UNCAPPED on this path) while the catalog/tags recorded `settings.temporalSamples` (4 at Standard) — every GUI archive frame rendered at ts≈1000 (~250× the tier's compute, the "hours" symptom persisting after v0.5.8) with mislabeled metadata. Fixed with the seam rework (all three plan builders take `settings.temporalSamples`, which `ExportSettings.resolve` already genome-defaulted + Metal-capped). Same class of bug as the export ts-default fix (v0.5.4): the RENDER path must consume the RESOLVED settings, never re-derive from the genome.
- **Framing normalization is a settings-level concern, NOT a renderer change (M6.6):** a `.flam3` genome's `camera.scale` is ABSOLUTE pixels-per-unit authored for the genome's `size` canvas — the renderers use it verbatim, so the same genome at 720p vs 4K framed differently (the resolution picker doubled as a ~3× zoom). The gen-248 data pins the ES authoring anchor to **WIDTH** (`scale/width` agrees to 2% across the 800×592 / 1280×720 / 1920×1080 populations; `scale/height` differs 34%), so `FlameKit.Framing.normalize(flame:renderWidth:)` (pure, rule #2-safe; identity when `renderWidth == size.x`) multiplies `scale` by `renderWidth/size.x`. Degenerate headers (unknown `size.x`, NaN/non-positive `scale` — the known gen-248 data-integrity class) pass through UNCHANGED. Threading: `ExportSettings.FramingMode` type-defaults `.faithful` (renderers/animate byte-unchanged — `git diff main -- Sources/FlameKit FlameReference FlameRenderer` shows only `Framing.swift` added, a binding M6.6 invariant); `export`/`flock` default `normalized` (`--framing faithful` restores raw scale, applied as a POST-resolve assignment — `ExportSettings.resolve` has NO framing parameter by design, mirroring how the GUI's `ExportManager.resolveSettings` does it); the GUI sheet's picker defaults Normalized; the flock archive is ALWAYS normalized (`FlockView.archiveSettings` + catalog framing exact hit-gate + `emberweft.framing` mdta tag — legacy rows MISS and re-render, never stitch mixed-framing). `animate` stays faithful always. **M6.7 (vertical/social presets) extends this with an orientation matrix:** portrait canvases (orientation DERIVED from the final canvas dims — `h > w` portrait, `w == h` square, never stored; `.custom` inherits) rotate landscape-authored genomes +90° and anchor the authored HEIGHT `size.y` (`FlameKit.Framing.apply(flame:renderWidth:renderHeight:framing:)`, the orientation-aware sibling; `normalize` stays byte-unchanged for the landscape-only preview/thumbnail surfaces). The rotation is CONDITIONAL on the authored-orientation mismatch (D3: portrait- and square-authored genomes are never rotated — identity/width-anchor — keeping `faithful`↔`animate` byte-identity for portrait-authored imports at native dims), applies in faithful mode too (portrait canvas = *raw scale, sideways*), and sits behind the same degenerate-header guard. CLI `--resolution` takes social tokens (`vertical720|vertical1080|portrait4x5|square1080`) + validated `WxH` (positive EVEN ints, 16…7680 × 16…4320; odd dims are silently CROPPED by VideoToolbox so parse time is the only clean guard; unknown/invalid values exit 2 — no silent 1080p fallback). Bitrates come from ONE pixel-band source (`VideoEncoder.autoBitrate` + `ExportCoordinator.autoBitrateMbps` both delegate; `.custom` dims reclassify from the flat fallback to their pixel tier). The flock framing gate `0/1/2` (legacy/faithful · normalized unrotated · normalized rotated; square = 1) is derived PER KEY via `FlockFramingGate` — canvas dims from the shard/row, NEVER `settings.resolution` (not guaranteed shard-aligned at the compare sites) — single-sourced across all four consumers (ArchiveRenderer write + mdta tag, Stitch + Generate compares). Catalog v4 is a VERSION RE-STAMP, not an ALTER (the `framing` column exists since v3): pre-M6.7 binaries are refused the WHOLE archive (`schemaVersionUnsupported`) instead of framing==1-MISS → re-render → clobbering gate-2 rows; migration steps are transactional; `rebuild` cross-checks each file's track `naturalSize` against its shard dims (mismatches are skipped + logged, never cataloged). Portrait shards are NEW cache identities (the shard name feeds `FlockSeed` → fresh seeds, no byte-reuse of landscape material).

## Module map (dependency direction: down)

```
FlameKit                       (genome model, .flam3 parse/serialize, interpolation)
  ├─ FlameReference            (CPU renderer: oracle + offline + fallback)
  └─ FlameRenderer             (Metal compute renderer)
       └─ FlamePlayer          (realtime adaptive playback)
            └─ FlameExport     (AVFoundation export)
                  └─ FlameFlock(M6.5 flock archive: flock.sqlite catalog, shard/naming, Generate/Stitch coordinators, ArchiveRenderer)

  └─ EmberweftGUI              (thin SwiftUI shell: emberweft-gui — NO test target)
EmberweftCLI                   (emberweft executable; --backend cpu|metal)
```

When unsure about scope, default to the smallest change that keeps the build green and the tests honest, and ask before large architectural moves.
