# M6.7 — Vertical / Social Presets: Design

> **Status:** approved design, 2026-08-25 · **Slice S10.7** (standalone, pulled forward from
> roadmap M8's "Vertical/social media presets" deliverable) · Predecessor pattern:
> [M6.6 framing normalization](2026-08-17-m6.6-framing-normalization-design.md).
>
> **Owner scope decisions (2026-08-25):** formats = 720×1280, 1080×1920 (9:16),
> 1080×1350 (4:5), 1080×1080 (1:1) — no 21:9. Surfaces = one-shot export + flock
> archive; portrait previews and aspect-aware library thumbnails are out of scope
> (follow-ups). Approach = genome-level rotated framing (rotate the camera +90° and
> swap the normalization anchor). CLI tokens = descriptive names.

## 1. Motivation

Social video is 9:16. TikTok, Instagram Reels, and YouTube Shorts all want
1080×1920, and Instagram's feed portrait wants 4:5 (1080×1350). Today every
resolution surface in Emberweft is landscape: the named `Resolution` cases, the
GUI export sheet tiers, the CLI `--resolution` tokens (which silently maps any
unknown token to `.p1080`), and `ShardPresets.sensible`. A vertical export is
reachable only through `.custom(w, h)` — which the GUI sheet's steppers cannot
even express (step-16 arithmetic from seeds 1920/1080 can never land on
1080×1920), and which frames as an unrotated width-anchored canvas: the authored
composition in a horizontal band with extended — usually empty — field above and
below.

The owner's framing requirement: portrait output must carry **the same
normalization semantics** as M6.6 — the authored composition preserved exactly,
with the genome's authored aspect ratio becoming irrelevant to framing.

## 2. Background — why rotation is the right lever

**M6.6 recap.** A `.flam3` genome's `camera.scale` is absolute pixels-per-unit
authored for the genome's `size` canvas. `FlameKit.Framing.normalize` rescales
`scale × renderWidth / size.x` (width anchor, data-pinned: gen-248 `scale/width`
agrees to 2% across populations, `scale/height` differs 34%), applied at the
plan-construction choke points before interpolation. Landscape framing is a
solved problem; this design extends it to portrait.

**The pipeline is already orientation-blind.** One `pixelsPerUnit` serves both
axes (CPU `ChaosGame.swift:230-234`, Metal `Kernels.metal:2144-2148`); the grid,
spatial filter, density estimation, and display kernels are square and
aspect-independent; Metal dispatches are per-axis ceil-div. A 1080×1920 canvas
renders correctly today — only the preset tables are landscape.

**Camera rotation is exactly the right transform.** `Camera.rotation` (degrees)
is applied identically on both backends as a 2×2 rotation of the world point
after subtracting `camera.center`, before scale. Consequences, all verified in
code:

- `+90` rotates content clockwise (standard CCW matrix in a y-down grid).
- The pivot is always `camera.center`, which lands on the exact canvas midpoint
  at any aspect ratio. The model has no `rot_center` (the parser drops the
  attribute), so there is no pivot ambiguity to handle.
- Rotation interpolates **linearly** through transitions
  (`GenomeInterpolator.swift:74`) — baking +90 onto *both* endpoints of a pair is
  constant across the morph — and is untouched during loops (`Loop.swift` rotates
  only xform pre-affines).
- No modulo exists on the angle; +90 rides along through parse → render →
  serialize harmlessly.

**The anchor must swap.** On a rotated portrait canvas, plain width-anchor
normalization computes `scale × 1080/1920 = 0.5625×` — a 1.78× zoom-out. The
correct portrait rule anchors the **authored height** (the authored vertical
axis becomes the canvas horizontal axis after rotation):

```
landscape:  effectiveScale = scale × canvasW / authoredW     (M6.6, unchanged)
portrait:   rotation += 90°; effectiveScale = scale × canvasW / authoredH
```

Exactness: a 1920×1080 genome on a 1080×1920 canvas gives factor 1080/1080 =
1.0 — pixel-for-pixel the authored composition, sideways, no resampling (the
chaos game projects directly onto the rotated canvas). For other authored
aspects the **anchored axis is still exact** and the mismatch lands on the other
axis, exactly as M6.6 already behaves in landscape:

| Authored | Portrait canvas | Result |
|---|---|---|
| 16:9 (1920×1080) | 9:16 (1080×1920) | exact fit, zero bands |
| 16:9 | 4:5 (1080×1350) | horizontal exact; top/bottom of the sideways composition cropped |
| 4:3 (800×592) | 9:16 | horizontal exact; extended field top/bottom |

A square canvas needs no rotation: width anchor, exact horizontal, vertical
extension — same rule as landscape.

**Rejected alternatives.** Post-render pixel rotation of the RGBA buffer
produces identical pixels but must be inserted at every sink (one-shot encoder,
`--frame --png`, the archive's resolution-alignment choke point) and splits
render dims from canvas dims — two sources of truth for one fact. Aspect-adaptive
zoom-to-cover (the old `docs/playback/formats.md` sketch) crops the authored
composition and fights authorial intent — M6.6 §2.4 already rejected that class.

## 3. The transform

Orientation is **derived from the final canvas dimensions, never stored**:
`height > width` → portrait, `width == height` → square, else landscape. Any
`.custom(w, h)` gets portrait semantics automatically.

| | `faithful` | `normalized` |
|---|---|---|
| **landscape** | identity *(today's code path)* | width anchor *(today's code path)* |
| **portrait** | `rotation += 90°` only | `rotation += 90°`; scale × canvasW / authoredH |
| **square** | identity | width anchor, **no rotation** |

- Rotation is the **preset's orientation semantic**, not part of the
  normalization choice: it applies in faithful mode too. "Authored" on a portrait
  canvas means *raw scale, sideways*.
- `+90°` (clockwise) is a single named constant. It is arbitrary for abstract
  flames; flipping it is a one-line change if renders look better the other way.
- **One guard gates the whole portrait transform, rotation included**: if
  `size.x ≤ 0`, `size.y ≤ 0`, `scale` is not positive-finite, return the flame
  unchanged (the known gen-248 degenerate-header class; those renders are black
  on both backends regardless).
- The rule is orientation-relative and agnostic to the genome's authored
  orientation (no ES population is portrait-authored, but a hypothetical one
  anchors consistently).
- Application sites are exactly M6.6's: `ExportCoordinator.buildRenderContext`
  (all video export + resume), `ArchiveRenderer.unitFlames` (archive, both
  endpoints before plan construction), and the CLI `--frame --png` mastering
  path. Applied before interpolation, so transitions blend rotated endpoints.
- Exact API shape (extend `normalize` vs a sibling `Framing.apply`) is left to
  the implementation plan; the pinned requirement is that both landscape cells
  delegate to today's behavior bit-for-bit.

## 4. Scope

**In:**

- `ExportSettings.Resolution` named cases: 720×1280, 1080×1920, 1080×1350,
  1080×1080; bitrate-table entries mapping each to its pixel-equivalent
  landscape tier (720×1280 → the 720p tier; 1080×1920, 1080×1350, 1080×1080 →
  the 1080p tier).
- GUI export sheet: four new tier entries — "Vertical 720p", "Vertical 1080p",
  "Portrait 4:5", "Square 1080". The framing picker is unchanged; the matrix
  defines what each choice means per orientation.
- CLI `--resolution`: named tokens `vertical720 | vertical1080 | portrait4x5 |
  square1080`, plus explicit `WxH` values (→ `.custom` with derived
  orientation), plus **error on unknown tokens** — replacing the silent
  `.p1080` fallback (aligning with the validated-flag precedent of `--fps` /
  `--framing`).
- `ShardPresets`: the four portrait entries; GUI shard menu grouped
  Standard / Vertical. The shard grammar, both shard-name parsers, `FlockSeed`,
  thumbnails, and catalog rebuild already accept `1080x1920_30fps` verbatim.
- Catalog schema **v4**: `framing` gate values `0` = legacy/faithful, `1` =
  normalized landscape, `2` = normalized rotated (portrait). Exact gate — a
  portrait shard hit requires `framing == 2`; legacy rows MISS and re-render.
  Written as `emberweft.framing` mdta `"2"`; read back on rebuild. Migration
  follows the v2→v3 ALTER-with-DEFAULT pattern.
- Flock browse-cell polish: `scaledToFit` so portrait thumbnails letterbox
  instead of cropping hard in the fixed-height cells (GUI-only, manual
  verification).
- Docs: roadmap M6.7 entry (M8 deliverable becomes a pointer),
  development-approach deferred-features note, README flag docs, CHANGELOG.

**Out (follow-ups, not committed):**

- Portrait preview presets and aspect-aware library thumbnails/cards (16:9
  surfaces stay landscape).
- 21:9 and other formats; HDR; duration/fps presets (defaults stay 30 fps,
  15 s loop / 12 s edge).
- GUI surface for faithful-portrait on the archive (CLI-only escape hatch).
- `rot_center` support (dropped by the parser today; irrelevant while the pivot
  is always `camera.center`).
- Export-sheet custom-dimension steppers reaching non-mod-16 dims (canonical
  portrait presets cover the real targets; `.custom` + CLI `WxH` covers the
  rest).

## 5. Locked decisions

| # | Decision |
|---|---|
| D1 | Genome-level rotated framing in pure `FlameKit.Framing` — not post-render pixel rotation, not zoom-to-cover (M6.6 §2.4). |
| D2 | Orientation is derived from final canvas dims (`h > w` portrait, `w == h` square), never a stored field; `.custom` inherits it. |
| D3 | Rotation is the preset's orientation semantic: `rotation += 90°` (clockwise, one named constant) applies in faithful mode too. |
| D4 | Portrait normalized anchor = authored **height** (`canvasW / size.y`). Square = width anchor, no rotation. |
| D5 | Both landscape cells of the matrix are today's code paths, byte-identical — M6.6 pins hold by construction. |
| D6 | Defaults unchanged: `FramingMode` type-defaults `.faithful`; product entry points default `.normalized`; `animate` never rotates or normalizes (no new flags). |
| D7 | Catalog framing gate: `0` legacy/faithful · `1` normalized landscape · `2` normalized rotated; exact hit-gate; schema v4 ALTER+DEFAULT; mdta `emberweft.framing` carries the value; rebuild parses it. A CLI faithful-portrait render records `0` — the owner-only mastering escape hatch, not orientation-distinguished (no GUI surface; verified 2026-08-25 that the live archive holds no portrait shards, only `1280x720_30fps` and `3840x2160_30fps`). |
| D8 | New `Resolution` cases are one-way checkpoint-compatible (old builds cannot decode new checkpoints; `.custom` round-trips as today). Documented, accepted. |
| D9 | CLI accepts `vertical720\|vertical1080\|portrait4x5\|square1080` + `WxH`; unknown tokens error (exit 2), no silent fallback. |
| D10 | The degenerate-header guard wraps rotation too — degenerate flames pass through entirely unchanged. |
| D11 | Portrait shards are new cache identities (shard name feeds `FlockSeed`): fresh seeds, no byte-reuse of landscape material — expected, not a bug. |
| D12 | Roadmap: standalone M6.7 / S10.7 pulled forward from M8; M8's vertical deliverable shrinks to a pointer. |

## 6. Invariants preserved

1. **Determinism (rule #2):** the transform is pure; preset lists are fixed
   arrays; no hashed-collection iteration anywhere new.
2. **`animate` untouched:** no resolution/framing/orientation flags;
   `animate` ↔ `export --framing faithful` byte-identity pins stay green.
3. **Engine parity untouched:** `git diff main -- Sources/FlameKit
   Sources/FlameReference Sources/FlameRenderer` shows `Framing.swift` only (the
   M6.6 invariant, extended to the portrait branch).
4. **Landscape framing unchanged:** all M6.6 framing tests pass unmodified.
5. **Stitch never mixes framing generations:** the gate is exact; portrait
   shards require `framing == 2`.
6. **Resume stability:** settings ride `ExportCheckpoint` as today; orientation
   is re-derived deterministically from the resolution dims at re-normalization.

## 7. Architecture (file map)

- **FlameKit** — `Framing.swift`: the portrait branch (rotate + swapped anchor)
  behind the degenerate guard; landscape branch untouched.
- **FlameExport** — `ExportSettings.swift`: four `Resolution` cases + width/
  height accessors + derived-orientation helper; `VideoEncoder.swift` and
  `ExportCoordinator.swift`: bitrate-table entries.
- **EmberweftCLI** — `ExportCommand.swift`: token parsing (named + `WxH` +
  error-on-unknown); `CLI.swift` help text.
- **FlameFlock** — `ShardPresets.swift`: portrait entries; `FlockCatalog.swift`:
  v4 migration; `FlockTypes.swift`: gate-value docs; `ArchiveRenderer.swift`:
  gate value from settings + derived orientation, mdta write;
  `StitchCoordinator.swift` / `GenerateCoordinator.swift`: gate compare.
- **EmberweftUI** — `ExportManager.swift`: nothing functional (resolution
  already threads); test hooks as needed.
- **EmberweftGUI** (no test target, manual verification) — `ExportSheet.swift`:
  tier entries; `FlockView.swift`: shard-menu sections, browse-cell
  `scaledToFit`.

## 8. Testing strategy

- **FlameKit framing pins** (`Tests/FlameKitTests/FramingTests.swift`, beside
  the M6.6 tests): 16:9 → 9:16 factor 1.0 + rotation 90; 4:3 → 9:16 anchor math;
  16:9 → 4:5 crop extent; square no-rotation + width anchor; faithful portrait
  = rotation only; degenerate passthrough (NaN scale, non-positive `size.y`)
  skips rotation too; landscape outputs identical to the M6.6 helper.
- **CLI parse tests** (beside `Tests/EmberweftCLITests/ExportFramingCLITests.swift`):
  each named token; `WxH`; unknown-token errors.
- **FlameFlockTests:** v3→v4 migration (and cascading v1→v4); exact gate — a
  portrait row with `framing < 2` MISSes and re-renders; mdta round-trip;
  portrait `ShardPresets` entries parse and carry dims.
- **EmberweftUITests** (`ExportOrientationUITests`, mirroring
  `ExportFramingUITests`): `resolveSettings` threads portrait resolutions;
  framing-choice semantics per the matrix.
- **Determinism pin:** a portrait shard rendered twice yields identical frames
  (existing per-artifact determinism pattern).
- **Manual:** sheet tier entries, shard-menu sections, browse letterboxing, and
  a real A/B social render (rotation-direction taste check) before release.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Sideways composition reads wrong on directional flames | A/B render real gen-248 sheep before release; direction and the rotation itself are one-constant flips; `suitable_for: vertical` seed metadata exists for future curation |
| Old checkpoints carrying new enum cases fail decode on old builds | D8: one-way compatibility, documented; `.custom` remains the interchange-safe encoding |
| Owner minted unrotated portrait shards via CLI during v0.6.x testing | D7's explicit gate value: those rows MISS against `framing == 2` and re-render — never silently stitched |
| Portrait archive starts cache-cold | Expected (D11): each portrait shard is a new namespace; Stitch MISS-render-into-archive handles it |
| GUI custom steppers still cannot express 1080×1920 | Canonical presets cover the real targets; CLI `WxH` covers the rest (out-of-scope note) |
| `formats.md` adaptCamera sketch describes behavior we did not build | Doc updated in the rollout pass to point at this spec |
