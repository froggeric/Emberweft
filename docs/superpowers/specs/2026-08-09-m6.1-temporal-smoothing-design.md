## Revision (2026-08-10): causal EMA → centered box window

Owner testing of the shipped EMA revealed a startup transient: the EMA is a
*causal* filter seeded cold at frame 0, so frame 0 is emitted sharp and smoothing
"ramps in" over ~τ = 1/α frames. **No causal filter can smooth frame 0** — that
requires future frames. The export is OFFLINE (stored video), so the industry-
standard fix is a **non-causal (centered) filter** (MIT Vision Book: *"a temporal
Gaussian is non-causal… not a problem when processing a video stored in memory"*).

**Decision (owner, 2026-08-10): replace the causal EMA with a centered BOX
(uniform) window** of half-width `h = round(1/α)` (Low→10 / Med→5 / High→3;
windows 21/11/7 — matching the EMA's effective span `N ≈ 2/α`). Per output frame
`m`, the smoothed histogram is the average over `[m−h, m+h]` (clipped at the
timeline boundaries). Frame `m` is emitted after frame `m+h` is rendered (latency
`h`, irrelevant offline).

**Why box (visual quality is the priority):** the per-frame flicker is i.i.d.
Monte-Carlo noise; the minimum-variance estimator over a window is the **uniform
(box) average** — it kills flicker harder than any center-weighted shape
(triangular/Gaussian) of the same width, replicating the warmed-EMA steady-state
quality the owner already validated. Box's theoretical drawbacks don't apply here:
sinc ringing needs sharp temporal edges (flame histograms morph smoothly → none),
and motion blur scales with window × speed (ambient loops barely move over a
0.3–0.7 s window → negligible; transitions are already motion-blurred via
`temporal_samples`). Box is also simplest + most robust (uniform running-sum, exact
`2h+1` window, no σ/truncation tuning). The window shape stays a one-line parameter
if triangular is ever wanted.

**Side benefits beyond fixing the startup:** zero-phase (no temporal lag — the EMA
lagged ~τ frames); **simpler/cheaper resume** — the window is local (`2h+1`), so
resume reconstructs it with an `h`-frame margin, NOT the EMA's full-window `[0,F)`
warmup (O(h) vs O(F)); no run-spanning accumulator.

**Memory:** `2h+1` Double histograms (Low/1080p ≈ 1.7 GB, 4K ≈ 7 GB) → RAM-guarded
(cap `h` / refuse over ~50% RAM, mirroring the loop-repeat guard).

**Affected tasks (re-implementation on branch
`m6.1-temporal-smoothing-centered`):**
- **T1 → T1′:** `HistogramEMA` is replaced by `TemporalBoxWindow` (ring buffer of
  `2h+1` histograms + running sum; `feed`/`emit`/`drain` API; shrinking boundaries
  at the timeline ends; `h`-frame emit latency). `TemporalSmoothing.halfWidth(for:) =
  round(1/α)`.
- **T8 → T8′:** the per-frame EMA dispatch becomes a **feed-emit** loop — feed each
  rendered frame's histogram; emit frame `m = n−h` once available; DISPLAY the
  emitted frame's center flame (`d_m`), not the fed frame's; append `reps×` for
  loops. The window is run-scoped (carries across segments + chunks), reset at the
  top-level body entries. The OFF path (`α ≥ 1.0` / `h == 0`) is the existing
  `renderImage`, byte-identical.
- **T9 → T9′:** the `[0,F)` full-window warmup becomes an **`h`-frame pre-roll
  margin** (re-render the `h` frames before the resume point to fill the window's
  lookback). O(h), cooperatively cancelable.
- **T2, T3–T7, T10–T12 UNCHANGED** — they produce/consume histograms + the toggle;
  only the coordinator's filter changes.

**Pins revised:** the cold-start pin CHANGES — frame 0 is no longer byte-identical
to OFF (it is now smoothed over `[0,h]`, which is the whole point of the change).
The Metal↔CPU parity (≥ 38 dB), loop-repeat+smoothing, cross-branch, and
resume-byte-identity pins stand. §9.5 (resumed == never-paused) holds via the
`h`-frame margin (the window is local).

This is the spec for the **across-frame histogram EMA** that removes the
"tiny dots moving around" flicker seen at low samples-per-pixel (spp). It is a
faithful, parity-preserving enhancement of the export pipeline. Every claim below
is verified against the code on `main` @ `v0.5.1` (`ab59a7479`).

## 1. Context

**Why this exists.** At low spp the export flickers: each frame's interpolated
genome walks a different chaos trajectory, so even with maximally-correlated
per-frame seeds the histogram jitters frame-to-frame. The owner's reported
symptom: "tiny dots moving around" at **Low (spp=2)** and **Medium (spp=8)**
quality; **High (spp=30)** is milder; **genome-default (spp≈1000, Metal-capped
64)** is "stunning" (no flicker). The flicker is trajectory divergence, NOT
reseeding — the per-frame thread-seed budget already correlates frames as much as
physically possible.

**The fix.** An **across-frame histogram EMA applied BEFORE the nonlinear display
pipeline.** Averaging histograms (linear density space) is unbiased (1/N variance
reduction); averaging AFTER gamma/log-density tone-map would bias (darken).
Flam3 renders each frame independently — this accumulates, so it is a deliberate
**renderer divergence** covered by the v0.5.0 owner decision that animation is
NOT flam3-parity-bound (amends rule #6; see CLAUDE.md). It is an *improvement on*
flam3, not a faithful port of it.

**What's already on `main` (verified — do not rebuild):**
- `Histogram` (`Sources/FlameKit/RenderTypes.swift:73`) is all-`Double`
  (`counts: [Double]`, `colors: [SIMD3<Double>]`, `alpha: [Double]`) with
  `accumulate(_:)` (elementwise add) and `scale(by:)` (elementwise mul) already.
  An EMA `H_acc = (1−α)·H_acc + α·H` is a trivial host-side Double operation —
  no new type.
- **CPU:** `ReferenceRenderer.render(blendAt:centerTime:temporal:sumfilt:params:)`
  (`Sources/FlameReference/ReferenceRenderer.swift:61`) builds the pre-display
  Double histogram internally (N chaos sub-passes → `hist.accumulate` → optional
  `DensityEstimation.apply(hist)` → `ToneMapping.render`). The split point
  ("build histogram" vs "display") is already a clean seam at the `hist`/`h`
  variable.
- **Metal — fused (export path today):** `renderFusedCore`
  (`MetalRenderer.swift:177`) and `renderTemporalFusedCore`
  (`MetalRenderer.swift:483`) encode chaos → decode → DE → log → display in ONE
  command buffer; the histogram lives in GPU **Float** buffers
  (`atomicBuf` → `floatBufA` → `floatBufB`), only RGBA read back. The PSO tuple
  is `(chaos, decode, density, log, display)` — five separate kernels, so the
  pipeline has a clean stage boundary after `decode` (the pre-DE Float histogram
  in `floatBufA`). The `atomicBuf` layout is `AtomicBinHost` (5×`UInt32`: count,
  r, g, b, a) — IDENTICAL to the layout `ChaosGameMetal.decode` expects.
- **Metal — unfused (parity reference, exists):** `ChaosGameMetal.iterate`
  (`ChaosGameMetal.swift:24`) → `DensityEstimationMetal.apply` →
  `DisplayPipelineMetal.render` (`DisplayPipelineMetal.swift:54`, which is
  `logDensity` + `displayPipeline`, takes a post-DE **Double** `Histogram`).
  `renderUnfused` (`MetalRenderer.swift:872`) composes them. **`FusedUnfusedParityTests`
  already pins fused-vs-unfused parity** — so "fused chaos + unfused (DE+display)"
  is a proven-equivalent route. **Caveats the readback design must respect
  (P1.3/P1.4):** (a) `ChaosGameMetal` is `@MainActor` and its `decode` is
  `private static` — not directly reusable from an actor-agnostic core; (b)
  `DensityEstimationMetal.apply` and `DisplayPipelineMetal.render` are
  `@MainActor` AND internally reach for `@MainActor` `MetalRenderer.deviceAndLibrary()`
  / `commandQueue` and build a fresh PSO per call — they cannot be "wrapped"
  off-main as-is.
- **Export loop:** `ExportCoordinator.renderFrames` (range walk, `loopRepeatCount`
  aware) and `renderFramesInterleaved` (resumable per-frame twin) own the per-frame
  `renderImage` dispatch. `renderImage` branches on backend + temporal.
- **Quality:** `ExportQualityChoice` (`Sources/EmberweftUI/ExportQualityChoice.swift`)
  maps `genomeDefault/low/medium/high` → `.genome/.spp(2)/.spp(8)/.spp(30)`.
- **Checkpoint:** `ExportCheckpoint` (`Sources/FlameExport/ExportCheckpoint.swift`)
  carries `settings: ExportSettings` (Codable) — so any smoothing decision added
  to `ExportSettings` rides in the checkpoint for free; resume reproduces it.
  **Caveat (P1.1):** `ExportSettings` currently uses SYNTHESIZED `Codable`
  (`ExportSettings.swift` has no custom `init(from:)`). A new non-optional field
  will throw `keyNotFound` on every pre-smoothing checkpoint unless a custom
  `init(from:)` decodes it via `decodeIfPresent` defaulting to `.auto`. This is
  load-bearing for resume and is called out in §4.4/§5/§9.

**Out of scope (do NOT pull in):**
- **Realtime preview smoothing.** The `PlaybackDispatcher` / `FlamePlayer` realtime
  path is UNTOUCHED this slice. (The preview flickers worse — its spp is even lower
  — but smoothing it is a later slice; scope discipline.)
- **Any change to renderer math (variations, chaos, DE, tone-map).** Smoothing only
  *interpolates histograms across frames*; it reuses every existing stage verbatim.
- **A new Metal shader.** Owner chose the **fused-path + readback** approach (see
  §2/D1) over a GPU-side EMA kernel — there is **no new `.metal` code**. The readback
  reuses the existing **`atomicBuf`** (the uint32 atomic-bin buffer the chaos kernel
  already writes), decoded on the host by the SAME logic the unfused path uses
  (extracted to a `nonisolated` helper, P1.4). It does NOT touch `floatBufA` /
  `floatBufB` (those are the GPU-side Float buffers the fused decode/DE PSOs write;
  the readback path skips those PSOs entirely).

## 3. The smoothing algorithm

### 3.1 EMA

Given the resolved α ∈ (0, 1] for the run and the per-rendered-frame pre-DE Double
histogram `H_current`:

```
H_acc = (1 − α) · H_acc + α · H_current        // elementwise over counts/colors/alpha
image = DISPLAY( DE( H_acc ) )                  // DE + log-density + tone-map, ONCE
```

- First rendered frame (cold `H_acc == nil`): `H_acc = H_current` — i.e. the
  first rendered frame passes through UNCHANGED (its displayed image equals the
  unsmoothed frame). This is a simple `nil → copy` rule, NOT the standard EMA
  "bias correction" (`acc / (1−(1−α)^t)`); we deliberately skip the first-frame
  blend so the export opens sharp and subsequent frames blend in. See §6.2.
- `DISPLAY∘DE` is the existing pipeline: CPU = `DensityEstimation.apply` then
  `ToneMapping.render`; Metal = `DensityEstimationMetal.apply` then
  `DisplayPipelineMetal.render`. Both consume a Double `Histogram` and are reused
  verbatim.

### 3.2 α resolution

`ExportQualityChoice` gains a `temporalSmoothingAlpha` derived entirely from the
quality tier (no user-tunable α this slice — the toggle is on/off/Auto only):

| Choice | spp | α | τ ≈ 1/α (frames) | smoothing |
|---|---|---|---|---|
| `genomeDefault` | genome (~1000, cap 64) | 1.0 | 1 | **OFF** |
| `high` | 30 | 0.35 | 2.9 | on (light) |
| `medium` | 8 | 0.20 | 5.0 | on |
| `low` | 2 | 0.10 | 10.0 | on (strong) |

### 3.3 OFF fast-path (byte-identity)

When smoothing is OFF (α ≥ 1.0 OR `range.count == 1` OR user toggle off),
`renderImage`'s OFF branch is the **existing** dispatch byte-for-byte — no
accumulator, no readback, no extra commits. (The PNG mastering path and `animate`
are smoothing-free a fortiori — they never enter the coordinator; see §4.5.) Every
animate↔export byte-identity pin routes through the OFF branch unchanged.

## 4. Architecture & data design

### 4.1 Accumulator lifecycle (`ExportCoordinator`)

A run-scoped optional Double histogram stored as a **`private var
smoothingAccumulator: Histogram?`** on the `ExportCoordinator` actor (NOT a
local — R4: `renderImage` is `async`, Swift forbids `inout` on `async` funcs,
and the smoothing-ON Metal step is two `await` hops with the EMA between them;
a local can't be mutated across that boundary). It is reset to `nil` at the top
of `renderFrames` / `renderFramesInterleaved` / `runResumableBody` (run-scoped
lifecycle) and discarded at run end. Actor serialization guarantees no
cross-run contamination (one run at a time).

- `renderFrames(range=1 path)` and `renderFramesInterleaved(resumable path)` each
  reset `smoothingAccumulator = nil` at entry and mutate it in place across the
  whole `range` (actor-isolated — no cross-actor hop needed for the mutation).
- For `runResumable` (chunked): `H_acc` is created at `runResumableBody` entry and
  carries across ALL chunks in the process. A resumed run (new process) creates a
  fresh `H_acc` and warms it (D7) before the first resumed frame.
- Fed once per **rendered** frame (loop-repeat replays bytes verbatim and does NOT
  re-feed the accumulator — the repeated copies are identical, so there is no
  inter-copy flicker to smooth). Under `loopRepeatCount > 1` the cached image is
  `DISPLAY(DE(H_acc))` at the single render point, replayed `reps×` (P2.3) — the
  accumulator is indexed by RENDERED global frame, never by output frame.

**Memory (P3.7):** `H_acc` is ONE `Histogram` for the whole run — not per-frame,
not per-segment, not multiplied by `loopRepeatCount`. At export `oversample == 1`
(`ExportQualityChoice` pins it) and the default `filterRadius == 0.5`, the grid is
`(width+2) × (height+2)` and each bin is `counts(8B) + SIMD3<Double>(24B) +
alpha(8B) = 40 B`. So `H_acc` ≈ **83 MB at 1080p**, **≈ 332 MB at 4K**. During
decode the path also transiently holds one `H_current` of the same size (plus the
GPU `atomicBuf` at 20 B/bin ≈ 166 MB at 4K), so peak smoothing-ON residency at 4K
is ≈ 0.8–1.0 GB. Bounded; does NOT grow with frame count. The existing
`checkLoopRepeatMemory` guard is unaffected (it sizes the loop-repeat RGBA cache,
a separate allocation the resumable/interleaved path does not build).

### 4.2 CPU path — `ReferenceRenderer` split

Extract the pre-display histogram build so the coordinator can EMA it:

```swift
// NEW: the chaos-temporal build, pre-DE. Mirrors the body of the existing
// render(blendAt:centerTime:temporal:sumfilt:params:) up to the `hist`/`h` seam.
public static func histogram(
    blendAt: (Double) -> Flame,
    centerTime: Double,
    temporal: [(delta: Double, weight: Double)],
    params: RenderParams
) -> Histogram
// and the single-flame twin:
public static func histogram(flame: Flame, params: RenderParams) -> Histogram
```

- The existing `render(blendAt:…)` and `render(flame:params:)` are reimplemented in
  terms of these (`histogram(...)` then DE then tone-map) — behavior byte-identical
  (pinned by the existing reference goldens). The split point is the existing
  `hist`/`h` local at `ReferenceRenderer.swift:82-113`; DE is `DensityEstimation.apply`
  and tone-map is `ToneMapping.render` with the SAME arguments the existing `render`
  passes (center-flame quality/camera + original-`params` `sampleDensity`). The new
  `histogram(...)` MUST also replicate the per-pass ISAAC seed salt and the
  `colorScalar = sub.weight` dmap rebuild verbatim — those are load-bearing for
  temporal blur and for N=1 byte-identity with the existing goldens.
- Coordinator smoothing-ON CPU step: `let h = ReferenceRenderer.histogram(blendAt:…)`,
  `ema(H_acc, h, α)`, then `DensityEstimation.apply(H_acc!)` + `ToneMapping.render(...)`.
  This runs inside the existing `Task.detached` CPU dispatch in `renderImage`; the
  EMA itself is a host-side Double op on the actor between the histogram return and
  the DE/ToneMapping call (CPU keeps DE/ToneMapping off-main in the same detached
  task — both are pure value-type functions).

### 4.3 Metal path — fused readback variants (D1/D5)

Two new actor-agnostic core functions, siblings of the existing fused cores, that
share the chaos+decode encoding via an extracted helper:

```swift
// NEW, actor-agnostic (mirrors renderFusedCore's extraction pattern):
static func renderFusedCoreToHistogram(
    flame: Flame, params: RenderParams,
    device: MTLDevice, queue: MTLCommandQueue,
    psos: (chaos:…, decode:…, density:…, log:…, display:…),
    seedBudget: MetalRenderer.ThreadSeedBudget?
) throws -> Histogram            // fused chaos → atomicBuf readback → host decode → Double

static func renderTemporalFusedCoreToHistogram(
    blendAt: (Double) -> Flame, centerTime: Double,
    temporal: [(delta: Double, weight: Double)], sumfilt: Double,
    params: RenderParams, device: MTLDevice, queue: MTLCommandQueue,
    psos: …, seedBudget: …
) throws -> Histogram
```

- They encode **chaos only** (single pass, or temporal N-pass accumulation into one
  `atomicBuf`), commit, then read `atomicBuf` back and decode it to a Double
  `Histogram`. The decode is the SAME logic the non-fused parity-proven path uses
  (`ChaosGameMetal.decode`: counts exact; r/g/b/a divided by `colorScale` into
  dmap-units), so the units are identical by construction — no new conversion to
  validate. They do NOT run the fused decode PSO, DE, log, or display.
  **(R8 — temporal loop must be byte-identical):** `renderTemporalFusedCoreToHistogram`
  replicates the temporal chaos loop of `renderTemporalFusedCore`
  (MetalRenderer.swift:637-714) BYTE-IDENTICALLY — same N-pass accumulation into
  ONE uncleared `atomicBuf`, same per-pass budget split (base+rem), same per-pass
  dmap rebuild with `colorScalar = sub.weight`, same per-pass threadSeeds salt
  (`params.seed &+ UInt64(i)` / `seedBudget.seeds(forPass:i,…)`), same per-pass
  threadCount/ipt/remainder, same full-budget `colorScale`. It differs ONLY in that
  it commits + reads back the `atomicBuf` after the chaos loop and encodes NO
  fused decode/DE/log/display. An implementer MUST NOT collapse it to a single
  pass or re-split the budget — that would silently break readback fidelity.
  **(R9 — zero-weight guard, precise reference):** `renderFusedCoreToHistogram`
  mirrors `renderFusedCore`'s zero-weight guard (MetalRenderer.swift:197-201) but
  returns an empty `Histogram` (instead of a black `RGBA8Image`).
  `renderTemporalFusedCoreToHistogram` has NO top-level zero-weight guard (it
  mirrors `renderTemporalFusedCore`, which has only a per-pass `continue` on a
  degenerate pass) — an all-degenerate flame yields a zeroed `atomicBuf` → an
  all-zero decoded histogram → the display step's all-zero guard (P2.5) emits black.
  **(P1.4 — extraction required, not just promotion):** `ChaosGameMetal.decode` is
  `private static` and the enclosing `enum ChaosGameMetal` is `@MainActor`. It
  CANNOT be called from an actor-agnostic core. Extract the decode (incl. the
  `AtomicBinHost` 5×`UInt32` layout, which is field-for-field identical to the
  fused path's `atomicBuf` layout) to a `nonisolated` helper — e.g. a free function
  `MetalHistogramDecode.decode(atomicBuf:binCount:gridWidth:gridHeight:colorScale:)`
  or a `nonisolated enum` — reused UNCHANGED by `ChaosGameMetal.iterate` (so the
  unfused path stays byte-identical) and by the new readback cores. The
  `colorScale` passed to decode MUST come from the FULL-budget `GPUFrameParams`
  (`fp.colorScale`), which the readback core builds exactly as
  `renderTemporalFusedCore` does (MetalRenderer.swift:592-594 — per-pass budget
  split, but `colorScale` stays full-budget so the atomic accumulation across N
  passes doesn't overflow the uint32 bins).
- **Off-main DE/display is a refactor, not a wrapper (P1.3; R1 fixes the access
  path + isolation):** `DensityEstimationMetal.apply` and `DisplayPipelineMetal.render`
  are `@MainActor` AND internally reach for `@MainActor` `MetalRenderer.deviceAndLibrary()`
  / `commandQueue` and compile a fresh PSO per call. There is nothing to "wrap".
  Extract `nonisolated static func` cores — **`DensityEstimationMetal.applyCore(_ hist,
  radius, minimum, curve, device, queue, densityPso)`** (the `nonisolated` is
  REQUIRED: the enclosing `enum DensityEstimationMetal` is `@MainActor` at line 14,
  so an unannotated `static func` inherits `@MainActor` and is NOT actor-agnostic),
  and **`DisplayPipelineMetal.renderCore(histogram:…, device, queue, logPso,
  displayPso)`** (`DisplayPipelineMetal`'s enum is NOT `@MainActor`, so this
  inherits nonisolated naturally — only `render` is `@MainActor`). The existing
  `@MainActor` `apply`/`render` become thin delegates that build device/queue/PSO
  from `MetalRenderer` state and call the `*Core` helpers — byte-unchanged.
  **Off-main orchestration is OWNED by `MetalRenderer` (R1):** `offMainCache`
  (MetalRenderer.swift:444) and `offMainQueue` (MetalRenderer.swift:439) are BOTH
  `private` to `MetalRenderer` — sibling types CANNOT read them. So the off-main
  DE+display step is a single **`MetalRenderer.renderSmoothedDisplayOffMain(histogram:
  Histogram, params:, flameForDisplay:) -> RGBA8Image?`** that runs on
  `offMainQueue.sync`, reads `offMainCache.handles()` + `offMainCache.pipelines()`,
  and calls the `nonisolated` `DensityEstimationMetal.applyCore` →
  `DisplayPipelineMetal.renderCore`. `DensityEstimationMetal`/`DisplayPipelineMetal`
  do NOT touch the cache or queue directly. (This also REMOVES the per-call PSO
  compile the current unfused entry points pay — the cached PSOs are reused.) This
  extraction is its own plan task and gets its own byte-identity pin (§9.3).
- **MainActor readback wrappers (R2 — the CLI path is unspecified without these):**
  the CLI coordinator renders Metal via the MAINACTOR branch (`useOffMainMetal ==
  false`, renderImage line 453). For smoothing-ON on the CLI (`--quality 2 --backend
  metal` is reachable), add MainActor wrappers
  **`MetalRenderer.renderHistogram(...)` / `renderTemporalHistogram(...)`** (thin,
  like `renderFused`/`renderTemporalFused`: build device/queue/PSOs from `MetalRenderer`
  state, delegate to the actor-agnostic `*CoreToHistogram`). The CLI smoothing-ON
  display step uses the EXISTING `@MainActor` `DensityEstimationMetal.apply` /
  `DisplayPipelineMetal.render` (already MainActor — no new display entry needed
  for CLI). The coordinator's ON-branch dispatches: `useOffMainMetal` → off-main
  wrappers + `renderSmoothedDisplayOffMain`; else (CLI) → MainActor wrappers +
  `apply`/`render`.
- Public off-main wrappers `MetalRenderer.renderHistogramOffMain(...)` /
  `renderTemporalHistogramOffMain(...)` mirror `renderOffMain` /
  `renderTemporalOffMain` (dedicated `offMainQueue` + `MetalOffMainCache`,
  returning `nil` on Metal-unavailable). They enforce the SAME box-only temporal
  guard as `renderTemporalOffMain` (return `nil` on non-box weights — P3.5).
- **Coordinator smoothing-ON Metal step is TWO off-main round-trips per frame
  (P3.3), with the EMA between them on the actor (R1: the second hop is a single
  `MetalRenderer` orchestrator that owns the queue+cache; R2: the CLI uses the
  MainActor twin):**
  ```
  // GUI (useOffMainMetal == true):
  h = await offmain { MetalRenderer.renderTemporalHistogramOffMain(…) }  // commit 1: chaos → readback → decode
  ema(self.smoothingAccumulator, h, α)                                  // actor, host-side Double (R4)
  img = await offmain { MetalRenderer.renderSmoothedDisplayOffMain(     // commits 2 + 3: DE then log+display
              histogram: self.smoothingAccumulator!, …) }               //   (owns offMainQueue + offMainCache)

  // CLI (useOffMainMetal == false) — R2:
  h = await MainActor.run { MetalRenderer.renderTemporalHistogram(…) }   // commit 1 (MainActor wrapper)
  ema(self.smoothingAccumulator, h, α)
  img = await MainActor.run {                                            // commits 2 + 3 via EXISTING @MainActor
              … DensityEstimationMetal.apply(…) … DisplayPipelineMetal.render(…) }
  ```
  i.e. 3 GPU commits/frame (chaos, DE, log+display) vs the fused path's 1 — the
  cost D1 accepts, confined to the smoothing-ON low-spp regime (P2.1). The
  off-main hops share `MetalRenderer.offMainQueue` so they serialize naturally
  (no extra synchronization); the MainActor hops share the main actor.

**Correctness pin (readback fidelity):** the new histogram-returning path, run at
α=1.0 (`H_acc = H_current`), must produce output within the existing fused-vs-unfused
parity band (already pinned by `FusedUnfusedParityTests`) of the inline fused path.
This proves the `atomicBuf` readback + Double promotion + unfused DE/display round-trip
is faithful. Note (P3.8): the readback reuses the SAME uint32→Double decode
quantization the fused path already has — smoothing introduces NO new Metal error
term; it only surfaces the existing one in the accumulator. (See §9.3.)

### 4.5 Mastering path gate

**The mastering paths are smoothing-free by CONSTRUCTION, not by a coordinator gate
(P2.2):**

- `export --frame N --png` renders the single frame DIRECTLY via
  `MetalRenderer.render` / `ReferenceRenderer.render` (`ExportCommand.swift:461-508`)
  — it never enters `ExportCoordinator`, never builds an `H_acc`, never imports the
  EMA helper. The CLI flag still forces `--temporal-smoothing off` on this path as a
  defensive double-lock.
- `animate` (`AnimateCommand.swift`) is a separate command with its own render loop;
  it has NO `FlameExport` dependency, so the EMA helper (which lives in FlameExport,
  §6.4) is unreachable from it. It is byte-untouched for free.
- A multi-frame `export` at `.genomeDefault` quality has α = 1.0 ⇒ the OFF fast-path
  inside the coordinator; byte-identical to a pre-smoothing build (the
  animate↔export byte-identity pin at genome-default still holds).

**In-coordinator belt-and-suspenders gate:** `renderFrames` /
`renderFramesInterleaved` compute `smoothingOn = (settings.smoothingAlpha < 1.0) &&
(range.count > 1)` at loop entry and reset `self.smoothingAccumulator = nil` (R4).
`range.count == 1` ⇒ OFF (covers a degenerate single-frame *video* export — rare,
but the guard is cheap). **(R4 — `renderImage` stays OFF-only):** `renderImage`
(`ExportCoordinator.swift:429`) is `async throws -> RGBA8Image` and CANNOT take an
`inout` accumulator (Swift forbids `inout` on `async` funcs); it is UNCHANGED
(byte-identical to today's 3-branch off-main/MainActor/CPU dispatch — every
animate↔export byte-identity pin routes through it untouched). The smoothing-ON

small actor-isolated helpers (`renderHistogramForFrame(descriptor:)` →
`ema(&self.smoothingAccumulator, h, α)` → `displayAccumulator(plan:params:flameForDisplay:)`),
mutating `self.smoothingAccumulator` in place; when OFF, the existing
`let img = try await renderImage(...)` path runs byte-for-byte. The zero-weight
guard (P2.5/R9) fires inside `displayAccumulator` before DE/display.

## 6. Determinism & parity analysis (the load-bearing section)

### 6.1 Determinism (rule #2)
`H_acc` at frame N is a pure function of (resolved α, genome, seed, params, and the
ordered sequence of frames 0…N). The EMA helper iterates sorted/contiguous arrays
(`Histogram.colors`/`alpha`/`counts` are arrays) — no `Dict`/`Set` float sums.
Resume rebuilds the identical `FramePlan` + `ThreadSeedBudget(baseSeed: params.seed)`
and re-feeds the same frames in the same order ⇒ identical `H_acc` ⇒ identical
output — **provided the warmup reconstructs the FULL accumulator state from the
export's cold start** (see §7; the original τ-window sketch did NOT achieve this
and is removed). The resolved α is serialized (via `settings`) so resume reproduces
it exactly.

### 6.2 Cold-start rule (pinned)
`H_acc` starts `nil`. The EMA helper: if `acc == nil`, `acc = current` (the first
frame is shown sharp, then subsequent frames blend). This is deterministic and
matches the natural "ramp-in" at an export's start. The alternative (init `H_acc`
to a zero histogram and apply the EMA from frame 0) would darken the first τ
frames by the (1−α)^N geometric tail; the `nil`→copy rule avoids that bias. Pinned
by a unit test asserting frame-0 output with smoothing ON equals frame-0 output
with smoothing OFF (cold start is a no-op for the first frame).

### 6.3 Metal↔CPU parity
The per-frame `H_current` on Metal comes from the `atomicBuf` readback + host
decode (uint32 atomic bins → Doubles via the `colorScale` division, the same
decode as the non-fused path); on CPU it is Double from `ChaosGame.iterate`. The
Float-vs-Double + atomic-quantization gap between them is the EXISTING Metal↔CPU
gap (smoothing changes nothing about it). The EMA (a Double linear
combination) preserves the existing per-frame Float-vs-Double gap — it does not
amplify it. DE+display then run on `H_acc` through the same Float(Metal)/Double(CPU)
stages as today. Net: Metal-with-smoothing vs CPU-with-smoothing stays within the
existing ~38 dB statistical parity class (the same class as the unsmoothed
Metal↔CPU relationship). Not byte-identical between backends (never was), not
required to be (rule #2). Pinned by extending the Metal↔CPU parity test to a
smoothing-ON fixture.

### 6.4 animate↔export byte-identity (mastering path)
Smoothing never touches the mastering paths: `animate` has no `FlameExport`
dependency (its own loop in `AnimateCommand.swift`), and `export --frame N --png`
renders directly (ExportCommand.swift:461-508) without entering `ExportCoordinator`.
Neither can reach the EMA helper or `H_acc`. A multi-frame export at genome-default
quality (α=1.0) takes the coordinator's OFF fast-path (`renderImage`'s OFF branch is
the existing dispatch byte-for-byte — no accumulator touched, no readback). Therefore
**every existing animate↔export byte-identity pin stays green unchanged.** The EMA
helper lives in `FlameExport` (not `FlameKit`) so `FlameKit` stays frozen and
`animate` cannot accidentally acquire a smoothing dependency.

### 6.5 Loop-repeat interaction
Loop-repeat (`loopRepeatCount > 1`) renders each loop frame ONCE and appends it
`reps×`. Smoothing feeds the accumulator once per RENDERED global frame; the
`reps×` appended copies are byte-identical (same `H_acc`), so there is no
inter-copy flicker and the repeat stays invisible. **The cached image is produced
by the smoothing-ON display step** (`DISPLAY(DE(H_acc))` at the render point),
then replayed `reps×` — an implementer must NOT bypass smoothing for cached loop
frames (P2.3). The cache-replay path (`renderFrames` repeat>1) and the
interleaved path (`renderFramesInterleaved`) both feed the accumulator at the
single render point per frame. Pinned by a loop-repeat + smoothing-ON
Metal↔interleaved parity test.

## 7. Pause/resume composition (with slice 1)

Slice 1's `runResumable` chunks the timeline, encodes each chunk, concatenates.
Smoothing composes as follows:

- **Within one process:** `H_acc` is created at `runResumableBody` entry and
  carried across every chunk (continuous — no per-chunk reset, no seam).
- **On resume (new process from checkpoint) — P1.5a full-window warmup (owner
  2026-08-09; R5/R6 harden the loop):** `smoothingAccumulator` is cold. The resumed
  run MUST end up with the SAME `smoothingAccumulator` at the first resumed global
  frame `F` that a never-paused run would have, or the §9.5 byte-identity pin is
  meaningless. Because the EMA is an IIR filter, `smoothingAccumulator` at `F`
  depends on ALL frames `0…F`, not just the last τ — so a short τ-window warmup
  `[F−τ, F)` is rejected (at α=0.10 its truncated tail `(1−α)^τ ≈ 0.35`, a ~35%
  residual, not byte-identical). Instead: **re-render histograms (images discarded)
  for every RENDERED global frame in `[0, F)`, starting from
  `smoothingAccumulator = nil` at frame 0** — this reproduces the original cold
  start exactly, frame-by-frame, so `smoothingAccumulator` at `F` is bit-identical
  to a never-paused run. Iterates RENDERED global frames (one feed each,
  independent of `loopRepeatCount`, P2.4), using the SAME `FramePlan` +
  `ThreadSeedBudget(baseSeed: params.seed)` the run rebuilt from the checkpoint
  (deterministic). `smoothingAccumulator` is NOT serialized (D7/D8 honored).
  **(R5 — warmup is a cancelable frame loop with progress):** the warmup is a loop
  over `[0, F)` that (a) checks `cancelled || Task.isCancelled` BETWEEN frames and
  throws `.cancelled` on cancel → the EXISTING cancel contract applies (GUI: the
  `consumeTask` `.cancelled` catch calls `discardCheckpointAndChunks`; CLI SIGINT:
  checkpoint + completed chunks kept for `--resume`); (b) yields
  `ExportProgress(phase: .rendering, currentFrame: w, totalFrames: F)` per warmup
  frame — reuses the existing `.rendering` phase (NO new `Phase` case; the GUI
  labels it "warming temporal buffer…" when `resumeFrom != nil &&
  smoothingOn`, since the same `.rendering` events drive the bar); (c) F==0 ⇒ the
  warmup body is empty (zero iterations) — the cold start at frame 0 IS the warmup.
  **(R6 — backend-dependent cost, honestly characterized):** cost = `F`
  histogram-only renders. On Metal each is low-spp/cheap (the chaos game scales
  with pixels×spp, and smoothing is ON only at low spp). On CPU (the CLI default
  backend, and the oracle) `ReferenceRenderer.histogram` is ~6–17 s/frame even at
  720p — a 1000-frame CPU warmup is HOURS, not "cheap". The spec recommends Metal
  for resumable+smoothing-ON runs; a CPU-backend resume paused late may be
  impractical, and abandoning its warmup degrades gracefully (cancel keeps the
  checkpoint for a later `--resume` or a Metal re-resume). The warmup is
  parallelizable across frames (each is independent until the EMA fold) but the
  EMA fold itself is serial — left to the implementer.
- **Checkpoint contents:** UNCHANGED structure (no `H_acc`, no schema bump). The
  resolved α rides in `settings.temporalSmoothing` + `settings.quality`; the only
  checkpoint change is the P1.1 `decodeIfPresent` for the new `temporalSmoothing`
  field (so v0.5.1 checkpoints decode to `.auto`).
- **`--resume` reproducibility:** the warmup replays frames `[0, F)` from cold, so a
  resumed+completed export is byte-identical (pixel-identical frames) to a
  never-paused export of the same job. Pinned by a resume-byte-identity test (§9.5).

## 8. Edge cases

| Case | Behavior |
|---|---|
| Quality = genome-default | Smoothing OFF (α=1.0); existing fused path byte-identical. |
| User toggles smoothing off at Low/Med/High | α forced to 1.0; OFF fast-path. |
| `range.count == 1` (single-frame video) | OFF regardless of α (belt-and-suspenders; the real mastering paths bypass the coordinator entirely — §4.5). |
| First RENDERED frame of a run / chunk 0 | Cold start: `H_acc = H_current` (sharp), then blends. |
| Resumed run | Reconstruct `H_acc` to never-paused equality via full-window warmup `[0,F)` (P1.5a) — §7. |
| Loop-repeat > 1 | Accumulator fed once per rendered global frame; cached image = smoothed frame, replayed `reps×` byte-identical (§6.5). |
| Transition segments | Accumulator carries continuously; transitions already temporally-blurred (`temporal_samples`), so the EMA adds mild extra smoothing (acceptable, often desirable). |
| Metal unavailable | Readback path is Metal-only; if Metal is unavailable the export uses CPU (smoothing works on CPU via the `ReferenceRenderer.histogram` split). No new failure mode. |
| Gaussian/exp temporal filter on Metal | The fused temporal path `fatalError`s / returns nil on non-box weights; the NEW readback temporal variant (`renderTemporalFusedCoreToHistogram` / `renderTemporalHistogramOffMain`) enforces the SAME box-only guard (P3.5). |
| Degenerate/zero-weight flame | The single-flame readback (`renderFusedCoreToHistogram`) short-circuits zero-weight to an empty `Histogram`, mirroring `renderFusedCore`'s guard (MetalRenderer.swift:197-201) but returning a Histogram instead of a black image (R9). The temporal readback has no top-level guard (mirrors `renderTemporalFusedCore`'s per-pass `continue`) — an all-degenerate flame yields a zeroed atomicBuf → all-zero decoded histogram. The smoothing display step detects an all-zero `smoothingAccumulator` and emits a black `RGBA8Image` DIRECTLY, bypassing DE/display (which would otherwise hit `log(0)` / `k2` divide-by-zero on an empty histogram — P2.5). No trap. |
| Empty/huge histograms | `H_acc` and `H_current` always share the run's grid dims (constant `params`); the EMA helper preconditions equal dims (mirrors `Histogram.accumulate`). 4K residency bounded at ≈ 0.8–1.0 GB (§4.1). |

## 11. Constraints honored (CLAUDE.md)

- **Reference-then-Optimize / parity:** no renderer math changed; smoothing reuses
  every existing stage verbatim. Metal↔CPU stays ≥ 38 dB (§6.3).
- **Determinism (rule #2):** accumulator is a pure function of (recipe, ordered
  frames); EMA iterates arrays only; α serialized for resume (§6.1).
- **No surprise external deps:** Apple SDKs only. No new packages. **No new `.metal`
  shader** (D1 readback reuses the existing `atomicBuf` + the proven decode).
- **Swift 6 strict concurrency:** the off-main DE/display path is a real
  `*Core` extraction (P1.3/R1: `nonisolated applyCore`/`renderCore` + a
  `MetalRenderer`-owned orchestrator) + a `nonisolated` decode helper (P1.4), NOT
  a wrapper; `smoothingAccumulator` is a `private var` on the `ExportCoordinator`
  actor (R4 — NOT a local: the ON dispatch is inlined into the frame loops because
  `renderImage` is `async` and can't take `inout`), isolated to one run via
  reset-at-entry + actor serialization.
- **Test-first:** each piece (EMA helper, CPU split, readback variant, coordinator
  integration, resume) gets its failing test before the implementation (§9).
- **Animation not parity-bound (v0.5.0 owner decision):** smoothing is a deliberate,
  owner-approved divergence from flam3's independent-frame rendering (§1).
- **Faithful flam3 port untouched:** variations, chaos, ISAAC, DE, tone-map are
  unchanged; smoothing operates strictly above them at the histogram-accumulator
  layer.
