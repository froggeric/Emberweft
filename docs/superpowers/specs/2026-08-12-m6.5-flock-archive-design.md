# M6.5 — Flock Archive + Stitching (Design Spec)

> Status: principal-reviewed and made developer-ready · 2026-08-12 · supersedes
> the one-shot-only export model for long-form output. Sibling to M6/M6.1 in the
> export family; standalone milestone **M6.5** between M6 and M7. The screensaver
> (M5) consumes this archive later.
>
> The archive **codec is HEVC (H.265) Main10** — decided 2026-08-12 after
> empirical evaluation (§8.1, §Codec evaluation). HEVC renders 10-bit, concatenates
> losslessly via `AVMutableComposition` passthrough (decode-clean, verified), and
> is ~40% smaller than H.264. H.264 is a deliverable option (one-pass transcode);
> ProRes is out (size). Each segment is rendered as a fresh independent encode
> (IDR at frame 0); segments are NEVER sliced from a longer render (ffmpeg slicing
> breaks HEVC POC/RPS, verified).

## 1. Motivation

A 5-genome sequence exported at genome-default quality took **over 3 hours**.
One-shot long-video export is unfeasible, and it **re-renders the same costly
material every time**. Electric Sheep solved this decades ago: it pre-generates
**loop** and **edge** videos, saves them locally, and composes long videos (and
its screensaver) from those saved files.

Emberweft does the same, with an ES-compatible naming scheme and two explicit
paths:

- **Path A — Generate:** render loops/edges *into* a local archive (batch /
  headless / overnight).
- **Path B — Stitch:** compose a long video *from* the archive, generating +
  archiving any missing material on demand.

The win: once a segment is rendered it is reused forever. Stitching pre-baked
material is a **no-reencode remux (seconds)**, not a render (hours). Even with
an empty archive, Path B never renders anything twice — every miss lands in the
archive first, so the archive grows monotonically smarter.

## 2. Scope

**In scope (M6.5):**
- The flock archive: naming, shard layout, catalog (`flock.sqlite`), per-artifact
  thumbnails, video metadata tags, user-configurable location.
- Path A (Generate) + Path B (Stitch), GUI + CLI.
- ES `<list>` XML interchange export (on-demand, per shard).
- **Decouple one-shot export from the preview window** — move it to a library-
  selection action; playback windows become play-only. (Folded in because we are
  already overhauling output UX.)
- Determinism + byte-stability pins; parity gate untouched.
- The **codec decision**: HEVC Main10 (§Codec evaluation, completed 2026-08-12).

**Out of scope (follow-ups):**
- The screensaver itself (M5) — it will *consume* this archive (play pre-rendered
  loops/edges instead of live-rendering). M6.5 only makes the archive
  screensaver-ready.
- Multi-quality coexistence within a shard (v1 uses the upgrade-overwrite rule,
  one best quality per artifact).
- A **configurable** archive codec — v1 fixes HEVC archive-wide. Letting shards
  differ by codec is a follow-up.
- Cross-archive / multi-machine sync.

## 4. Architecture

```
FlameKit   (genome model, Loop.blend, Transition.blend, FramePlan, Schedule,
             Segment, FeatureVector, edges.sqlite pair oracle — UNCHANGED, frozen)
   |
FlameExport (ExportCoordinator, VideoEncoder, concatChunks, TemporalBoxWindow,
             ThreadSeedBudget — REUSED + two small ADDITIVE extensions in §14.2)
   |
FlameFlock  (NEW, sibling to FlameExport: catalog, shard/naming, GenerateCoordinator,
             StitchCoordinator, ArchiveRenderer, ListXmlExporter, IdMinter)
   |
EmberweftUI (FlockModel + testable store/types — NEW)  ←  EmberweftGUI (FlockView,
             thin wiring — NEW, manual-test only — NO test target)
```

**The dispatch boundary is the `Segment`** (a loop segment, or an edge/transition
segment) — already the unit `FramePlan`/`Schedule` expose. Path A renders one
segment into the archive; Path B, per segment, hits the archive or renders the
miss into the archive, then concatenates.

```
genomes (.flam3) + edges.sqlite (pair oracle, ~75,743 edge rows / ~74,864 pairs)
        |
   [Path A: Generate] ----render one segment--->  Flock archive  (mpeg/ + jpeg/ + flock.sqlite)
        |                                                  ^
        |                                                  |  (misses also write here first)
   [Path B: Stitch] --per segment: HIT->use / MISS->render-into-archive--> passthrough concat --> long video
```

Both paths render through `FramePlan` + the existing render primitives via a new
`ArchiveRenderer` entry. **No renderer math is touched** (parity gate clean).

### 4.1 The lone-edge render construction (verified against the code)

`Schedule` strictly alternates loop,transition by segment id parity and **segment
0 is always a loop** (`Schedule.appendNextSegment`, `Sources/FlameKit/Schedule.swift`).
Therefore a lone edge is **NOT expressible as a 1-segment `FramePlan`**. The
correct, verified construction (the one `ArchiveRenderer` uses):

- **Loop artifact** (self-edge, `a==b`): one `FramePlan` with `segmentCount: 1`
  and `flames: [A]`. Segment 0 is `loop(A)`. Render global-frame range
  `0..<framesPerSegment`. Each frame's `descriptor(for:)` returns `.loop` with
  `blendAt` bound to `Loop.blend(A, t:cycles:)`. Done.

- **Edge artifact** (`A→B`): one `FramePlan` with `segmentCount: 2` and
  `flames: [A, B]` (selector `Sequential` walks A→B at segment 1). Segment 0 is
  `loop(A)` (NOT rendered), segment 1 is `transition(A→B)`. Render global-frame
  range **`framesPerSegment ..< framesPerSegment + transitionFramesPerSegment`**
  only (the transition slot of pair 0). `Schedule.frameToBlend` maps those frames
  to `.transition` descriptors with the correct 1-indexed `blend ∈ (0,1]`, and
  `FramePlan.descriptor(for:)` binds `blendAt` to
  `Transition.blend(A, B, t:stagger:rotationVelocityRatio:)`.

- **Velocity match is preserved across standalone and timeline renders.**
  `FramePlan.descriptor(for:)` computes `rotRatio = Double(transitionFramesPerSegment)
  / Double(framesPerSegment)` from the **plan's per-kind frame counts**
  (`FramePlan.swift:80`), independent of `segmentCount`. So a standalone 2-segment
  edge plan feeds `Transition.blend` the **same** `rotationVelocityRatio` the
  full stitch timeline does — the archive's edge byte-matches the edge rendered
  inline in a one-shot export. This is the key correctness invariant for stitch
  byte-stability and is pinned (§17).

- The realtime `PlaybackDispatcher` passes the same `r`, so preview matches the
  archive and the eventual export. (CLAUDE.md: "separate loop/transition
  durations + rotation velocity-matched easing".)

`ArchiveRenderer` MUST render the transition range and **drop** the loop-slot
frames entirely (never encode them, never write them to disk). The 2-segment plan
is constructed solely because `Schedule` requires a loop before a transition.

### 4.2 Reaching the render primitives (the `renderFrames` visibility fix)

`ExportCoordinator.renderFrames`/`renderImage`/`feedEmitSmoothed`/
`displayAccumulator` are `private` to the `ExportCoordinator` actor
(`Sources/FlameExport/ExportCoordinator.swift`). The archive cannot call them
directly, and it must NOT reimplement the 3-branch (off-main Metal / MainActor
Metal / CPU) dispatch (parity + byte-identity risk). So FlameExport gets **one
small additive entry** (§14.2) used by both the existing `runJob` and the new
`ArchiveRenderer`: a `public` range-into-URL render that wraps the existing
private primitives without changing them. This keeps the per-frame path single-
sourced (the byte-identity and parity pins stay meaningful).

## 5. Naming & layout (grounded in real ES files)

### 5.1 What ES actually does (verified `/Volumes/ssd/ElectricSheep/content/mpeg`)

ES video files are `<gen>=<id>=<a>=<b>.<ext>` (separator `=`), e.g.
`10247=18169=18038=18036.avi` is edge `18169` from sheep `18038`→`18036`; a loop
is the degenerate `10247=18040=18040=18040.avi` (`id==a==b`). Verified against the
5,316 files in `/Volumes/ssd/ElectricSheep/content/mpeg/`. The XML catalog
confirms it: `<sheep id="18169" first="18038" last="18036">`. Resolution lives at
the **list** level (`<list gen="10248" size="1280 720">`), not the filename.
`edges.sqlite` carries the pair→edge_id map (table `edge_pairs`, columns
`edge_gen, edge_id, a_gen, a_id, b_gen, b_id`).

### 5.2 Emberweft naming (ES-inspired, not byte-identical)

Emberweft **drops `edge_id`** and uses the 4 fields for the two endpoints
(think: two `(gen,id)` pairs), so **cross-generation edges work** and the ordered
pair *is* the cache key:

```
<a_gen>=<a_id>=<b_gen>=<b_id>.<ext>

loop   ES 248/00628              248=00628=248=00628          (a==b)
edge   248/00628 → 248/03194     248=00628=248=03194
edge   248/00628 → user 00042    248=00628=900000=00042       (cross-gen, native)
loop   user 900000/00042         900000=00042=900000=00042
```

**Why endpoint-grouped `(a_gen,a_id,b_gen,b_id)` and not gens-first
`(a_gen,b_gen,a_id,b_id)`:** gen stays adjacent to its id (readable as two pairs);
lexicographic sort groups edges by source sheep; parses into adjacent
`(f1,f2)`/`(f3,f4)` pairs; loop detect = `a_gen==b_gen && a_id==b_id`.

**Encode/decode (deterministic, rule-#2-safe):**
- `encode`: `"\(aGen)=\(aId)=\(bGen)=\(bId).\(ext)"`. ES ids/gens preserved
  verbatim (e.g. `"248"`, `"00628"`); minted ids zero-padded to 6 digits
  (`"000042"`); minted flock gen is `"900000"`. Mixed digit-widths are fine (parse
  splits on `=`).
- `decode`: split the stem on `=`; require exactly 4 fields; `(aGen,aId,bGen,bId)`;
  `kind = .loop iff aGen==bGen && aId==bId` else `.edge`. Any file that does not
  parse to exactly 4 `=`-fields is **skipped + logged** by the catalog scan
  (resilience; never an abort). Each field is additionally validated as
  `[0-9]+` (the `=`-split already rejects `/`, `..`, etc., but the digit gate
  rejects stray text).

**Path safety.** Shard names are validated to `^[A-Za-z0-9_]+$` at construction
(`FlockNaming.shardDir` rejects bad input). Archive-relative paths are built by
joining `flockRoot` + shard + `mpeg`/`jpeg` + the filename, and the resolved path
is checked to be **inside** `flockRoot` (resolves symlinks via
`resolvingSymlinksInPath()`, rejects `..` escape). This mirrors `BatchPath.resolve`
(the existing D13 path-traversal gate in FlameExport). `flockDir` itself is
standardized and symlink-resolved at load.

**Cost vs ES:** not strict-ES-filename-compatible (ES field 2 was `edge_id`).
ES interchange is delivered by the on-demand list-XML export (§9), which recovers
real ES `edge_id`s for ES-sourced pairs from `edges.sqlite`. Accepted (D1).

### 5.3 Archive layout

```
<flock-root>/                      <- AppPreferences.flockDir (default <app-support>/Flock/)
  flock.sqlite                     <- catalog (source of truth; rebuildable from below)
  1920x1080_30fps/                 <- SHARD dir: WxH_fps (canonical 15s/12s => duration omitted)
    mpeg/
      248=00628=248=00628.mov       <- loop (HEVC, .mov)
      248=00628=248=03194.mov       <- edge
      248=00628=900000=00042.mov    <- cross-gen edge
      900000=00042=900000=00042.mov <- loop, user genome
    jpeg/
      248=00628=248=00628.jpg       <- representative-frame thumbnail per artifact
      ...
  1280x720_30fps/                  <- another resolution shard
    mpeg/ …
    jpeg/ …
  1920x1080_30fps_Lf495-Tf300/     <- NON-canonical pace shard (loopFrames 495, transFrames 300)
    mpeg/ …
```

The file **extension** follows the shard's archive codec via
`Codec.requiresMOVContainer` (ProRes ⇒ `.mov`; H.264/HEVC ⇒ `.mp4`). A shard's
codec is uniform, so its extension is uniform.

**Shard-dir name** (deterministic function of the shard tuple):
`"<W>x<H>_<fps>fps"` + (unless canonical) `"_Lf<loopFrames>-Tf<transFrames>"`.
Canonical means `loopSeconds==15.0 && transSeconds==12.0` (⇒ `loopFrames==
round(15*fps)`, `transFrames==round(12*fps)`). Frame counts (integers) are used in
the suffix, not seconds, for rule-#2 determinism; the seconds are stored in
`shards`.

### 5.4 Video file metadata tags (NEW capability on `VideoEncoder`)

`VideoEncoder` today writes NO file-level metadata
(`Sources/FlameExport/VideoEncoder.swift` — `start()` creates the writer and never
sets `writer.metadata`). M6.5 **extends** `VideoEncoder` (§14.2) to accept an
optional `[AVMetadataItem]` and assign it to `writer.metadata` before
`startWriting()`. Each artifact then carries:
- `title` = the filename stem (mirrors ES),
- `artist` = `Emberweft`, `software` = `Emberweft <version>`,
- Emberweft keys: `emberweft.spp`, `emberweft.ts`, `emberweft.smoothing`,
  `emberweft.smoothing_hw`, `emberweft.quality_rank`, `emberweft.source`,
  `emberweft.source_sha`, `emberweft.seed`, `emberweft.rendered` (ISO date).

Standard keys (`title`/`artist`/`software`) use `AVMetadataItem` with the
`commonKey` space. The `emberweft.*` keys use a custom keySpace (`"emberweft"`)
with each key string as `key`. These let `flock rebuild` regenerate
`flock.sqlite` from `mpeg/` + tags alone. The metadata-write path is covered by a
`canEncode`-style probe + a round-trip test (read tags back via `AVURLAsset`).

## 6. Catalog schema (`flock.sqlite`)

```sql
CREATE TABLE flock_meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);  -- 'schema_version'='1', 'created_at', 'next_minted_id'

CREATE TABLE shards (
  name          TEXT PRIMARY KEY,    -- dir name
  width         INTEGER NOT NULL,
  height        INTEGER NOT NULL,
  fps           INTEGER NOT NULL,
  loop_seconds  REAL NOT NULL,
  trans_seconds REAL NOT NULL,
  loop_frames   INTEGER NOT NULL,
  trans_frames  INTEGER NOT NULL,
  is_canonical  INTEGER NOT NULL,    -- 1 iff 15s/12s
  codec         TEXT NOT NULL        -- 'proRes422HQ' | 'h264' | 'hevc' (archive codec)
);

CREATE TABLE sheep (
  gen          TEXT NOT NULL,        -- ES gen ('248') or '900000' (Emberweft)
  id           TEXT NOT NULL,        -- ES id verbatim, or minted 6-digit
  origin       TEXT NOT NULL,        -- 'es' | 'user'
  source_ref   TEXT,                 -- .flam3 URL/path (NULL if unknown)
  source_sha   TEXT,                 -- SHA-256 of source bytes (identity)
  display_name TEXT,
  added_at     INTEGER NOT NULL,
  PRIMARY KEY (gen, id)
);

CREATE TABLE artifacts (
  a_gen        TEXT NOT NULL,
  a_id         TEXT NOT NULL,
  b_gen        TEXT NOT NULL,
  b_id         TEXT NOT NULL,
  shard        TEXT NOT NULL,        -- FK shards.name
  kind         TEXT NOT NULL,        -- 'loop' | 'edge'   (loop iff a==b)
  file         TEXT NOT NULL,        -- path under flock-root, e.g.
                                     -- '1920x1080_30fps/mpeg/248=00628=248=03194.mov'
  thumb        TEXT,                 -- relative jpeg path
  width        INTEGER NOT NULL,
  height       INTEGER NOT NULL,
  fps          INTEGER NOT NULL,
  loop_frames  INTEGER NOT NULL,
  trans_frames INTEGER NOT NULL,
  spp          INTEGER NOT NULL,
  temporal     INTEGER NOT NULL,
  smoothing    TEXT NOT NULL,        -- 'off' | 'auto'
  smoothing_hw INTEGER NOT NULL DEFAULT 0,
  quality_rank REAL NOT NULL,        -- effective sampling (upgrade ordering)
  bytes        INTEGER NOT NULL,
  rendered_at  INTEGER NOT NULL,
  source_sha   TEXT,                 -- SHA of source genome(s) used (re-render identity)
  seed         INTEGER NOT NULL,     -- deterministic seed used (see §10)
  codec        TEXT NOT NULL,        -- archive codec of this artifact
  PRIMARY KEY (a_gen, a_id, b_gen, b_id, shard),
  FOREIGN KEY (shard) REFERENCES shards(name)
);
CREATE INDEX idx_artifacts_shard ON artifacts(shard);
CREATE INDEX idx_artifacts_a ON artifacts(a_gen, a_id);
CREATE INDEX idx_artifacts_b ON artifacts(b_gen, b_id);
```

The `artifacts` primary key **is** the cache key (D2). The primary access pattern
is lookup-by-pair within a shard (the stitch dispatcher); indexes on `a`/`b`
support "edges involving this sheep." `completed`/set-like fields (e.g. resume
bookkeeping, `completedChunkIndexes`) are stored **sorted** wherever used
(rule #2; mirrors `ExportCheckpoint.encode(to:)` which sorts
`completedChunkIndexes`).

**Concurrency / serialization.** `FlockCatalog` is an `actor` (one serialized
writer). `GenerateCoordinator`/`StitchCoordinator` (also actors) hold a `FlockCatalog`
reference and all catalog mutations go through it — no concurrent writes, no
SQLite `SQLITE_BUSY`. GUI reads go through `FlockModel` (`@MainActor @Observable`),
which snapshots the catalog via a `@MainActor` `refresh()` that hops onto the
catalog actor and returns a value-type `FlockSnapshot`. The GUI never reads
SQLite directly. This is the same pattern as `ExportManager` (an `@MainActor`
VM driving an actor coordinator).

**Migrations.** `flock_meta.schema_version` gates schema evolution. A version
mismatch on open ⇒ back up the old file, then `flock rebuild` from `mpeg/` +
tags. The archive is never opaque.

**Resilience.** Corrupt/missing `flock.sqlite` ⇒ rebuild from `mpeg/` filenames +
video tags (`flock rebuild`, and a "Rebuild catalog" action in Browse). A file in
`mpeg/` that doesn't parse to 4 `=`-fields, or whose tags are missing, is skipped
+ logged (count surfaced in Browse).

## 7. Id model & minting

- **ES-sourced genomes** keep their real `(gen,id)` (e.g. `("248","00628")`),
  read from the `.flam3` path/name at import. No minting.
- **User/curated/imported genomes** (anything without a real ES identity) get a
  minted id in reserved flock `900000`: `("900000", "<next, 6-digit>")`. The
  counter persists in `flock_meta.next_minted_id`. Minted **once**, recorded in
  `sheep`, never reassigned (stable identity ⇒ no regeneration). `900000` is
  clearly non-ES (ES gens observed ≤ `10248`), so a collision with a future ES id
  is impossible as long as ES never reaches gen `900000` (documented; if it ever
  does, the reserved range moves — the `sheep.origin` column makes the split
  unambiguous).
- **Edges** have no id at all (D1); their identity is the ordered pair. For an
  ES-sourced pair, `edges.sqlite` is consulted only (a) as a *pair oracle* for
  selection, and (b) at list-XML export to recover the real ES `edge_id`.
- `sheep.source_sha` (SHA-256 of the `.flam3` bytes) is the re-render identity:
  if a source file changes, the catalog row is invalidated (matches the existing
  export resume SHA-256 gate in `ExportCoordinator.reparseSources`).

## 8. Quality model & archive codec

### 8.1 Archive codec — HEVC (H.265) Main10 (decided 2026-08-12)

The archive/stitched-master codec is **HEVC Main10, 10-bit** (`yuv420p10le`),
decided after empirical evaluation (§Codec evaluation). Reasons: ~40% smaller
than H.264 at equal visual quality (decisive at TB scale), Apple-Silicon hardware
encode/decode (VideoToolbox), 10-bit Main10 on-ramps the M8 HDR plan, and
visually equal to H.264/ProRes at the tuned bitrates. The codec is **uniform
within a shard**, and lossless passthrough concat (`AVMutableComposition` +
`AVAssetExportPresetPassthrough`, the existing `concatChunks`) was verified
decode-clean for independently-encoded HEVC segments. Archive container: `.mov`.

**Master vs deliverable:** the archive holds the HEVC master. A deliverable is a
one-pass transcode — HEVC for size, **H.264 for max decode compatibility**, ProRes
for a lossless master. YouTube/TikTok/Instagram re-encode every upload, so upload
codec is a non-issue; direct-sharing edge cases are covered by the H.264
deliverable transcode.

**Render-independently, never slice (load-bearing):** each archive segment is
rendered as a FRESH `VideoEncoder` session whose frame 0 is an IDR keyframe. The
`ArchiveRenderer` builds a per-unit `FramePlan` (1-segment loop, or 2-segment
edge emitting only the transition slot, §4.1) and feeds just that slot's frames
to a fresh encoder. Segments must NOT be extracted by slicing a longer render
with ffmpeg `-c copy` — verified that slicing breaks HEVC POC/RPS at the cut
(decoder errors `Duplicate POC`, `Could not find ref with POC`). Independent
per-segment encodes concat cleanly (verified: 2- and 3-segment, decode-clean).

### 8.2 Quality tier (effective spp)

The quality tier (`genome` / `high` / `standard` / `low`, i.e. effective spp) is
per-artifact metadata (`quality_rank`), **not** a shard dimension and **not** in
the filename.

### 8.3 Upgrade-overwrite rule (D4)

When a generate or a stitch-miss would render an artifact, compare the requested
`quality_rank` to the stored one:
- requested **>** stored ⇒ render and **overwrite** at the same path;
- requested **≤** stored ⇒ **hit** (skip).

So the archive holds only the best-so-far per `(shard, pair)` and self-improves.

`quality_rank` = effective sampling = `spp × temporal × √(2·smoothing_hw + 1)`
(genomes-default resolves to its `samplesPerPixel`). Higher = better; comparable
across tiers. (Deterministic; rule-#2-safe.) The codec is NOT part of
`quality_rank` (it is a shard-wide constant, not a per-artifact dimension).

## 9. ES interchange (on-demand list-XML export)

`flock export-list --shard <name> [--flock <dir>]` writes, beside the shard:
- a `<list gen=… size="W H">…<sheep id=… first=… last=… rating=… url=…/>…</list>`
  in the ES format (one entry per artifact, `url` = the `.mov`/`.avi` filename),
- for ES-sourced edges, the **real ES `edge_id`** recovered from `edges.sqlite`.

**Edge counts (verified `genomes/electric-sheep/edges.sqlite`, table
`edge_pairs`):** 75,743 edge rows over 74,864 distinct ordered pairs. There are
**364 ordered pairs that carry duplicates** (879 surplus edge rows; the most-
duplicated pair has 32 edge rows). On a duplicate, `export-list` emits the
**lowest `edge_id`** for stability (deterministic, recorded in `flock_meta`).
Cross-generation: **255 cross-gen edge rows / 223 distinct cross-gen pairs**
(`a_gen != b_gen`). These are first-class in the Emberweft name (no special
handling); for list-XML they synthesize an `edge_id` (no ES original exists).

This is a **derived** artifact (D5); `flock.sqlite` remains the only primary
catalog. "Best-effort" interchange (D1): pure-ES shards at the ES house format
are the most interchangeable; mixed shards export with synthesized edge ids.

## 10. Determinism & byte-identity

- **Per-artifact determinism (rule #2):** each artifact is rendered through a
  `FramePlan` (loop: 1 segment; edge: 2 segments, transition range only — §4.1)
  with a **deterministic seed** `seed = sha256ToUInt64("shard|aGen|aId|bGen|bId")`.
  The seed helper (new, tiny, in `FlameFlock`) computes SHA-256 over the canonical
  UTF-8 string and reads the first 8 bytes little-endian as a `UInt64`. This is a
  pure string→Int hash (no Swift `Dictionary`/`Set` iteration, no per-process
  hash randomization) ⇒ rule-#2-safe. Same artifact + same `RenderSpec` ⇒
  identical bytes, run-to-run and machine-to-machine. The seed is threaded into
  `RenderParams.seed` (the existing field) and into `ThreadSeedBudget(baseSeed:)`,
  matching the export path's `params.seed` invariant.
- **Stitch byte-stability:** the stitch output is a passthrough concat of
  deterministic artifacts ⇒ identical sequence + shard ⇒ identical output bytes
  across runs (the concat is a pure function of its same-byte inputs).
- **Pair-keyed, never regenerated:** rendering the same pair twice produces one
  file (the second is a hit/overwrite, decided by `quality_rank`).
- **animate ↔ export byte-identity pin: UNAFFECTED.** The archive is a new path
  (segment-range renders into archive-named files via the new `ArchiveRenderer`
  entry); the existing one-shot export (`ExportSheet` → `runResumable`) still
  pins to `animate` exactly as before. The OFF (smoothing-off) archive path uses
  the same `renderImage` primitive, byte-identical to the export OFF path.
- **Parity gate UNAFFECTED:** no edit under `Sources/FlameKit|FlameReference|
  FlameRenderer`. `FramePlan`/`Schedule`/`Segment`/`Loop`/`Transition` are
  *used as-is*, not modified. FlameKit stays frozen. (Verified by `git diff` at
  merge time showing no engine files.)

## 11. Path A — Generate

**Purpose:** pre-bake material into a shard so future stitches are instant.

**Flow:**
1. Pick a **shard** (resolution/fps/pace/archive codec; default
   `1920x1080_30fps` canonical at the interim ProRes default), a **source** (a
   collection, a set of genomes, or explicit/discovered pairs), a **scope** (D10:
   default *edges*; opt-in *loops* or *loops+edges*), and a **quality tier**.
2. Enumerate the units: loops (one per genome) and/or edges (the pairs —
   consecutive-in-order, all-pairs, or similarity-selected via `edges.sqlite`/
   `FeatureVector`). Unrenderable genomes are skipped (the `isRenderable` health
   gate, `Sources/FlameKit/GenomeHealth.swift`); a skip notice is recorded.
3. For each unit, by `(shard, pair)`: hit-at-≥-quality ⇒ skip; else render one
   segment via `ArchiveRenderer` (the new FlameExport entry → `FramePlan` +
   private render primitives + `VideoEncoder` at the shard codec), write to the
   **archive-named path** (`FlockNaming.archiveFileURL`, NOT through
   `ExportCheckpoint.sanitizedStem`), write the `.jpg` thumb, embed video tags,
   fsync + atomic-rename, THEN upsert the `artifacts` row (never a catalog row
   without its file). Progress reports skip/render counts.
4. Long batches reuse checkpoint/resume-style chunking (the GenerateCoordinator
   writes a generate-plan file listing pending units; cancel/resume re-reads it).

**CLI:** `emberweft flock generate --shard <name> --from <collection|dir|flam3…>
[--scope edges|loops|both] [--quality …] [--codec …] [--flock <dir>]`.

## 12. Path B — Stitch

**Purpose:** compose a long video from the archive (fast if cached).

**Flow:**
1. Pick a **shard** + a **sequence** (collection / ordered list / playlist) +
   output container; target length is derived (`#sheep × pace`) or a frame budget.
2. Build the alternating `Schedule` (`loop A · edge A→B · loop B · …`).
3. **BATCH-lookup all segment keys against `flock.sqlite` ONCE up front** (one
   parameterized `SELECT … WHERE (a_gen,a_id,b_gen,b_id,shard) IN (...)`), not per
   segment — avoids N+1 and gives the upfront HIT-vs-will-generate count for the
   progress banner. For each segment, keyed by `(shard, pair-or-sheep)`:
   - **HIT** (≥ requested quality, same codec) ⇒ collect the archive file;
   - **MISS** ⇒ render the segment **into the archive first** (Path-A-style),
     then collect.
4. **Codec-uniformity gate.** All collected files MUST share the shard's codec.
   A codec mismatch (e.g. a leftover file from a pre-codec-change archive) ⇒
   refuse + point the user at `flock rebuild` (or overwrite via a generate pass).
   This is the precondition for…
5. **Passthrough concat** the collected files (reuse `ExportCoordinator.concatChunks`
   — `AVMutableComposition` + `AVAssetExportPresetPassthrough`) → output. No
   re-encode (uniform HEVC/fps/res within the shard). Passthrough concat for HEVC
   was verified decode-clean on independent segments (§Codec evaluation), so this
   step is a lossless remux and the perf premise holds.
6. Progress reports **HIT vs generated** counts up front and as it runs — the
   "3-hour problem" visibly vanishes (a fully-cached sequence stitches in
   seconds). Optional final transcode to H.264/HEVC deliverable.

**Edge cases:** EMPTY sequence ⇒ user-facing "nothing to stitch" error, no file
written. SINGLE-genome sequence ⇒ loop-only (no edges), one segment, no concat
needed (copy/rename the cached loop, or render then concat one file).
Cross-shard stitch ⇒ refused (uniform format required; UI/CLI enforce it).

**CLI:** `emberweft flock stitch --shard <name> --sequence <collection|order>
[--out file.mov|file.mp4] [--deliver h264|hevc] [--flock <dir>]`.

## 15. Conventions honored (CLAUDE.md)

- **Reference-then-Optimize / parity:** no engine file touched; render primitives
  reused via the single additive entry. Parity gate not required (verified by
  `git diff`).
- **Determinism (rule #2):** deterministic seed is SHA-256-truncation over a
  canonical string (pure); catalog lookups are by key / parameterized batch SQL;
  `quality_rank`/counts are scalars; no float sums over hashed collections;
  `completed`/set fields sorted on encode; catalog mutations serialized by the
  `FlockCatalog` actor. Pinned.
- **No external deps:** Apple SDKs only (Foundation, SwiftUI, AppKit, AVFoundation,
  CoreMedia, CryptoKit). `flock.sqlite` via the built-in SQLite3 (already a system
  lib; same as `edges.sqlite` reads).
- **Swift 6 strict concurrency:** `FlockCatalog`/`GenerateCoordinator`/
  `StitchCoordinator` are `actor`s; `FlockModel` is `@MainActor @Observable`;
  Metal hops via `Task.detached { MetalRenderer.renderOffMain }` (the existing
  off-main path) inside the FlameExport render-range entry, never blocking the
  MainActor; `MetalRenderer.isAvailable` is probed via
  `await MainActor.run { MetalRenderer.isAvailable }` from the coordinators' async
  context (never from a non-main actor/sync method — it traps). No
  `DispatchSemaphore.wait` in async contexts.
- **Test-first:** each slice's tests red before green.
- **Faithful flam3 port / animation-not-parity-bound:** the archive ports no new
  renderer behavior; it caches the existing (already-faithful) loop/edge output.
  Animation motion model unchanged.
- **FlameKit stays frozen / animate acquires no new dependency:** the archive
  lives in `FlameFlock`/`FlameExport`; `animate`'s path is untouched.

## 16. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Archive grows huge | Configurable `flockDir`; Browse size readout + per-shard/per-artifact delete; HEVC's measured size (§Codec evaluation) is the size-management input. |
| `flock.sqlite` corruption/loss | Rebuildable from `mpeg/` + video tags (`flock rebuild`); filenames + tags self-describe identity. Atomic write (temp → rename → upsert) so a crash mid-render never leaves a catalog row without its file. |
| Determinism break (rule #2) | SHA-256 seed; key-based lookups; serialized catalog; pinned determinism + byte-stability tests. |
| Loss of strict ES filename interchange | Accepted (D1); on-demand list-XML export recovers real `edge_id`s for ES pairs. |
| First stitch of an unbaked sequence is slow | Progress shows HIT vs generated up front; reuse accumulates; Path A pre-bakes the expensive edges. |
| Minted-id collision with future ES ids | Reserved flock `900000` (clearly non-ES); documented; `sheep.origin` makes the split unambiguous. |
| Video-tag write/read across codecs | `VideoEncoder` metadata extension is codec-tested; `canEncode`-style probe + round-trip read for HEVC (the chosen archive codec). |
| Cross-shard stitch requested | Refuse: stitching requires a single shard (uniform format); UI/CLI enforce it. |
| Codec-mismatched file in a shard (leftover) | Codec-uniformity gate (§12 step 4) refuses + points at `flock rebuild`. |
| Crash mid-render orphans catalog | Catalog upsert happens AFTER the atomic rename; a generate-plan file lists pending units for resume. |
| SwiftUI sheet teardown leaks GPU work | Coordinators are actors held by `FlockModel` (AppModel-owned, survives teardown); strong-self stop path (M4 lesson). |
| `DispatchSemaphore` in async | Not used; the render-range entry is `async` and uses `Task.detached` + the existing `PixelBufferPool.acquire` helper where needed. |

## 17. Testing & Definition of Done

**Automated (new):** every criterion names an observable and a verify command.

## §Codec evaluation (completed 2026-08-12 — HEVC chosen)

**Decision: HEVC (H.265) Main10** as the archive/master codec (owner, 2026-08-12,
after the empirical run below). H.264 is the max-compat deliverable transcode;
ProRes is a lossless-master option. See §8.1 for the mastering workflow.

The owner empirically encoded real sheep at 720p/1080p/1440p/4K (low quality,
~15 s loop). Measured per-loop size:

| codec | 720p | 1080p | 1440p | 4K |
|---|---|---|---|---|
| HEVC | 52 MB | 104 MB | 163 MB | 300 MB |
| H.264 | 83 MB | 164 MB | 250 MB | 500 MB |
| ProRes 422 HQ | 213 MB | 424 MB | 640 MB | 1280 MB |

All three visually good at the tuned bitrates (v0.5.0 encoder-finetuning already
validated quality). ProRes is ~4x HEVC, disqualified at TB scale; HEVC is ~60%
the size of H.264.

**Concat gate (GATING) - PASSED for HEVC.** Two loops + an edge rendered as
independent `VideoEncoder` HEVC `.mov` segments (720p, Main10, 10-bit), then
concatenated via the faithful `concatChunks` mirror (`AVMutableComposition` +
`AVAssetExportPresetPassthrough`, the exact API Emberweft uses):

- `[loopA, loopB]` -> 30.000 s / 900 frames, full-decode CLEAN (zero errors).
- `[loopA, loopB, loopB]` (independent encodes, the archive's exact pattern) -> 45.000 s / 1350 frames, full-decode CLEAN.
- Sizes add losslessly (passthrough, no re-encode): 47 + 48 MB -> 95 MB stitched.

**Negative finding (load-bearing - drives the `ArchiveRenderer` design):**
slicing a segment out of a longer render with `ffmpeg -c copy` BREAKS HEVC at the
cut (the sliced segment errors on decode at the seam: `Duplicate POC`, `Could not
find ref with POC`). The archive MUST render each segment as a fresh independent
encode (each starting on an IDR frame), never slice. (Also observed: the ffmpeg
`concat` demuxer produced a broken 865 s file from the same `.mov` inputs, an
ffmpeg `.mov` edit-list artifact; AVFoundation, which Emberweft uses, is correct.)

---

The remainder records the pre-decision methodology that produced the above data:

For each candidate — **(a) ProRes 422 HQ**, **(b) H.264 High AutoLevel at a high
bitrate with a 1-sec GOP**, **(c) HEVC Main10 AutoLevel at a high bitrate** —
measure, using the REAL export path (`MetalRenderer.renderOffMain`/`
renderTemporalOffMain` + a reused `MetalRenderer.ThreadSeedBudget`, NOT the
`@MainActor` `MetalRenderer.render` which rebuilds PSO+seeds per call and is
~4–5× slower, per CLAUDE.md):

1. **Bytes per artifact + projected archive size.** Render ~10 loops and ~10
   edges at 1080p and at 4K, canonical pace (15 s loop / 12 s edge @ 30 fps),
   for each codec. Report mean bytes/artifact and the projected size of a
   realistic flock (200 loops + 200 edges). This is the size-management input.
2. **Passthrough concat (GATING).** Using our `VideoEncoder`, produce two
   same-codec segments, then run `ExportCoordinator.concatChunks`
   (`AVMutableComposition` + `AVAssetExportPresetPassthrough`). Verify the result
   has BOTH segments' frames at the right PTS and that NO re-encode happened
   (inspect `AVAssetTrack` codec + that the export was passthrough). If an
   inter-frame codec (H.264/HEVC) cannot passthrough-concat two same-codec
   segments produced by our encoder, **stitching re-encodes and the whole perf
   win evaporates** — that codec is rejected unless the owner accepts re-encode.
3. **Quality on high-frequency fractal content.** BPP and PSNR vs a ProRes
   reference on a spiky attractor (e.g. a `244.*` fixture). Recall fractal detail
   smears under low BPP (the v0.5.0 reason for raising H.264/HEVC bitrates ~5×).
4. **Random-access / seek cost for Browse thumbnail extraction.** Time to decode
   one representative frame from the middle of a segment (intra vs inter-frame
   matters: ProRes is intra-frame, cheap random access; inter-frame codecs must
   decode from the nearest keyframe).

**Decision rule (the rule the run above applied):** the smallest codec whose (2)
passthrough concat succeeds AND whose (3) fractal quality is acceptable. The run
found all three acceptable on quality, HEVC smallest with concat verified, so the
decision (2026-08-12) is HEVC Main10 — applied throughout this spec (§8.1, D12).

Wherever the build references the codec, it reads a single source
(`ExportSettings.Codec` for the shard) and the file extension follows
`Codec.requiresMOVContainer` (ProRes ⇒ `.mov`; H.264/HEVC ⇒ `.mp4`).
